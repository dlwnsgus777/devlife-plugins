## 0. 코드 구조 정비 (Tidy First) — 기존 코드 수정 시만 작성

> 요구사항이 기존 설계 안에서 무리 없이 들어갈 목표 구조로 기존 코드를 먼저 옮긴다. 정비 커밋은 기능 커밋과 **반드시 분리**한다.
> 목표 구조는 Step 2에서 사용자와 함께 고른 것만 적는다. 기존 틀과 설계를 뜯어고치는 변경은 정비가 아니다.
> 지금 구조로 무리 없이 들어가면 **`해당 없음 — [지금 구조로 어떻게 반영되는가]`**라고 적는다.
> 결정 근거에는 사용자가 그 목표 구조를 고른 이유를 적는다.

**결정 근거**: [예: 채널이 분기마다 늘어나므로, 정비 비용보다 이후 채널 추가가 쉬워지는 이득이 크다]

| 목표 구조 | 기존 코드 정비 (기법) | 영향 범위 (호출부·안전망 테스트) | 본 작업에서 추가할 것 |
|---------|-------------------|----------------------------|-------------------|
| [예: 채널별 수수료를 `FeePolicy` 구현체가 계산한다] | [예: `SettlementService`의 채널 분기 3개를 구현체로 추출한다 — Replace Conditional with Polymorphism] | [예: `SettlementService`, 호출부 `SettlementController`·`BatchSettler` / `SettlementServiceTest`] | [예: `NewChannelFeePolicy` 구현체] |

**커밋 순서**: `refactor: [정비 내용]` → `feat([티켓]): [기능 내용]`

### 비즈니스 불변성

> 구현 전 과정에서 절대 깨져서는 안 되는 규칙을 **완성된 문장**으로 작성한다.
> 불변성이 깨졌을 때 어떤 문제가 생기는지 함께 서술한다.
> 출처는 `[문서]` / `[사용자확인]` / `[코드추론]` 중 하나 — `[코드추론]`은 근거가 코드뿐이라는 뜻이므로 검토 우선순위가 가장 높다.
> `[사용자확인]`은 사용자가 실제로 답한 경우에만 붙인다.
>
> **격리 불변성**: 같은 기능의 기존 구현이 운영 중이고 신규 구현은 별도 테이블을 쓴다면
> "신규 코드는 기존 테이블을 읽거나 쓰지 않는다"와 **그 역방향**을 각각 불변성으로 적는다.
> 요구사항 문서나 사용자 답이 분리를 정했을 때만 적는다.
> TDD 스킬이 이 불변성을 받아 양쪽 경계를 검증하므로, 여기 적으면 검증이 따라온다.

| 불변성 | 위반 시 영향 | 출처 |
|-------|------------|------|
| [예: 승인 완료된 계약의 금액은 어떠한 경우에도 변경될 수 없다] | [예: 정산 불일치와 감사 실패] | `[사용자확인]` |
| [예: 계약 해지 요청은 원계약이 존재하는 상태에서만 가능하다] | [예: 고아 해지 레코드 생성] | `[코드추론]` |
| [격리 예: 신규 처리는 기존 `legacy_table`을 갱신하지 않는다] | [예: 데이터 오염·정산 불일치] | `[문서]` |
| [역방향 예: 기존 처리는 신규 `new_table`을 갱신 대상으로 조회하지 않는다] | [예: 역방향 오염] | `[문서]` |

## 3. 기존 코드의 함정 (답습 금지)

> 참조할 기존 구현에 결함이 있으면 여기 적는다. **적지 않으면 AI는 기존 코드를
> "이 프로젝트의 정답"으로 읽고 그대로 복제한다.**
> 각 항목은 문제 진단으로 끝내지 말고 **`→ 신규는`까지** 쓴다 — 지시가 없으면 대안을 임의로 발명한다.
> 참조할 기존 구현이 없거나 결함을 찾지 못했으면 **`해당 없음`이라고만 적는다.**

**현재 코드**
- `[경로:라인]` — [무엇을 하는가] (위치마다 한 줄)

**왜 문제인가**: [재현 조건 / 경계값 / 인덱스·성능 영향 — 한 문장]

> 표는 입력에 따라 결과가 틀리는 결함일 때만 쓴다. 그 밖에는 생략한다.

  - `[ServiceClass.method()]` ← [용도]

### 코드 스니핏

> 클래스 선언, `private final` 필드, 메서드 본문을 적는다.
> 메서드 본문에는 호출 순서, 불변성마다 지키는 가드 절, 예외, 반환 형태를 적는다.
> 로깅, 트랜잭션 설정, 방어적 null 체크는 생략한다.
> 요구사항을 다시 읽지 않고 코딩을 시작할 수 있을 만큼 쓴다.
> 재사용 스캔이 찾은 클래스를 주입한다.
> 클래스명·메서드명은 위 파일 테이블, 섹션 8 구현 항목과 일치해야 한다. 대상 클래스가 여러 개면 블록을 반복한다.

```java
@Service
@RequiredArgsConstructor
public class [ClassName] {

    private final [ExistingReadService] [readService];  // 재사용 — 조회 + 미존재 시 예외

    public [ResponseType] [methodName]([RequestType] request) {
        [Entity] [entity] = [readService].getById(request.get[Entity]Id());

        // [불변성 문장]
        if ([위반 조건]) {
            throw new [DomainException]([에러 코드]);
        }

        [entity].[도메인 메서드]([인자]);

        return [ResponseType].from([entity]);
    }
}
```

## 8. 구현 순서 (TDD)

> 테스트 설명은 도메인 규칙 문장으로 쓴다. 테스트 설명은 테스트 결과에 표시되는 문장이다.
> 예: ~~"testCancelWhenPaid"~~ → **"결제 완료된 주문은 취소할 수 없다"**
> 섹션 2의 모든 불변성이 여기 테스트로 한 번 이상 나와야 한다.
> 테스트를 추가하기 전에 Step 1 결과의 기존 테스트가 그 동작을 이미 검증하는지 확인한다.
> - `[NEW]` — 다루는 기존 테스트가 없음. 새로 쓴다.
> - `[REGRESSION]` — 기존 테스트가 다룸. 그대로 실행한다. 중복 테스트를 추가하지 않는다.
> 섹션 0의 정비는 1단계에서 기존 케이스에 대해 한다. 새 케이스는 2단계에서 추가한다.
> 정비 대상에 기존 테스트가 없으면, 1단계 맨 앞에 현재 동작을 고정하는 테스트를 `[NEW]`로 둔다.
