# GPT 오케스트레이터 하네스 설계

GPT(Codex CLI)가 지휘하고 Claude Code(Opus)가 작업하는 cmux 기반 멀티 모델 하네스.

## 목적과 사용 맥락

- **목적**: 멀티 모델 지휘 방식을 직접 실험하고, **교차 모델 검토**(작업한 모델이 아닌 다른 모델이 검증)가 실제로 효과가 있는지 확인한다. 자동 루프·컨텍스트 분리·원장은 Claude 단독으로도 가능하므로, 이 하네스의 고유 가치는 교차 검토에 있다.
- **사용자**: 우선 본인 단독 사용. 단 마켓플레이스 배포가 가능해야 하므로 개인 경로나 개인 CLAUDE.md/AGENTS.md 내용을 전제하지 않는다.

## 성공 기준

- 요청 하나로 문서 작성 → 승인 → 위임 → 검증 → 완료가 사람 개입 없이 진행된다.
- 막히면(재시도 상한 도달, 워커 무응답 등) 원인과 함께 사람에게 명확히 보고된다.
- 실행 기록(지시·결과·재지시 파일)으로 오케스트레이터가 워커의 무엇을 잡아냈는지 사후에 확인할 수 있다.

## 범위

| 포함 | 제외 |
|---|---|
| 워커 1개, 순차 실행 | 워커 병렬화 |
| 오케스트레이터의 테스트 직접 실행 검증 | |
| 작업 간 워커 컨텍스트 초기화(`/clear`) | |
| cmux 사이드바 진행률과 알림 | |

## 실행 흐름

```
[사람] 요청
   ↓
[오케스트레이터] 문서 작성 — 요청 크기에 따라 plan-creator 또는 spec-creator 선택 (사람과 대화)
   ↓
[사람] 승인  ← 사전 승인 지점
   ↓
[오케스트레이터 ↔ 워커] 작업 위임 → 수행 → 테스트 검증 → 다음 작업 (반복)
   │  └ 막히면 → [사람]에게 보고하고 대기
   ↓
[오케스트레이터] 최종 결과 보고 → [사람]
```

- **plan 경로**: plan 하나 승인 → 그 plan의 작업들을 자동 루프로 수행.
- **spec 경로**: spec 승인 후, 하위 작업마다 `plan-creator`를 대화형으로 돌려 **각각 승인**받는다. 즉 "plan 작성 → 승인 → 루프"가 하위 작업 단위로 반복된다. 이 방식이라 `plan-creator`를 수정 없이 재사용한다.

## 아키텍처

```
┌─ cmux workspace ──────────────────────────────────────────────┐
│ [Codex pane] 오케스트레이터         [Worker pane] 워커           │
│  devlife-orchestrator 스킬           claude --agent devlife-worker│
│   ├ spec-creator / plan-creator       (허용 도구만, 질문 금지)    │
│   └ cmux 스킬 (pane·사이드바·알림)                                │
│        │  신호: cmux send 한 줄 ─────────▶ │                     │
│        │ ◀───────── 신호: codex queue 한 줄 │                     │
│        └───────── devlifeteam/<run-id>/ ───┘  (내용은 모두 파일)  │
└───────────────────────────────────────────────────────────────┘
```

- 두 모델은 **cmux(신호)와 파일(내용)로만** 연결된다. 서로의 내부 동작을 알 필요가 없다.
- 오케스트레이터 모델명은 하드코딩하지 않고 사용자의 Codex 실행 설정(`codex -m` 또는 `config.toml`)에 맡긴다. 기본으로 상정하는 모델은 `GPT 5.6 terra`(사양 미확인).

## 컴포넌트

| 컴포넌트 | 위치 | 책임 |
|---|---|---|
| `devlife-orchestrator` 스킬 (신규) | `codex/skills/devlife-orchestrator/SKILL.md` | 준비 → 문서 → 승인 → 루프 → 보고 흐름 전체 |
| 오케스트레이터 정책 (신규) | `codex/skills/devlife-orchestrator/references/orchestrator-policy.md` | 직접 코딩 금지, 재시도 상한 2회, 보고 시점, 검토 기준, 테스트 금지 규칙 예외 |
| 인계 템플릿 (신규) | `codex/skills/devlife-orchestrator/assets/` (`task.md`, `result.md`, `ledger.md`) | 지시·결과·원장 형식 |
| 워커 에이전트 (신규) | `agents/devlife-worker.md` | 워커 모드 규칙, 허용 도구 목록(`tools`), `model: opus` |
| `cmux` (재사용) | `codex/skills/cmux` | pane 생성·전송·화면 읽기, 사이드바, 알림 |
| `spec-creator`, `plan-creator` (재사용) | `codex/skills/` | 승인 대상 문서 작성 |

기존 `devlife-codex`, `devlife-team-starter`(Claude 지휘 방향)는 재사용하지 않고 그대로 둔다.

### 핵심 결정

- **정책은 스킬의 `references/`에 두고 스킬 시작 시 로드**: 오케스트레이터 모드는 스킬을 시작했을 때만 켜져야 하고, 플러그인으로 그대로 배포되며, 작업 프로젝트의 `AGENTS.md`를 건드리지 않는다.
- **워커 규칙은 Claude 에이전트로 정의**: `claude --agent devlife-worker`로 메인 세션 자체를 워커로 실행한다. 시스템 프롬프트(워커 모드 규칙)와 허용 도구를 한 파일로 묶는다. 권한은 명시한 목록으로 제한한다(auto·skip-permissions 모드 사용 안 함).
- **워커 모드 규칙**: 사용자에게 질문하지 않는다. 계획이나 피드백 요청을 하지 않는다. 막히면 결과 파일의 "막힌 점"에 적고 종료한다. 완료하면 결과 파일을 쓰고 알림 명령을 실행한다.
- **테스트 실행 금지 규칙 예외**: 전역 `CLAUDE.md` §3과 `codex/AGENTS.md` §3의 "Never run tests after writing them"은 하네스 실행 중에는 적용하지 않는다. 정책과 워커 에이전트 양쪽에 명시한다.
- **대기 방식**: 워커가 완료 후 `codex queue --thread <오케스트레이터 세션> --message "<작업ID> done"`으로 알린다. 확인 실험에서 동작하지 않으면 결과 파일 폴링으로 대체한다.

## 데이터 흐름

### 파일 구조

신호(한 줄)만 터미널로 오가고, 내용은 모두 파일로 주고받는다. 긴 텍스트를 터미널로 직접 보낼 때 생기는 이스케이프·잘림 문제를 피하고, 실행 기록을 남기기 위해서다.

```
devlifeteam/<run-id>/
├── ledger.md                              작업 목록, 상태, 재시도 횟수
├── tasks/    T01.md, T01-retry1.md, T02.md …
└── results/  T01.md, T01-retry1.md, T02.md …
```

| 방향 | 신호 | 내용 |
|---|---|---|
| 오케스트레이터 → 워커 | `cmux send`: `/clear`, "`tasks/T01.md`를 읽고 수행" | `tasks/T01.md`: 목표, 수정 범위, 완료 조건, 결과 파일 경로, 알림 명령 |
| 워커 → 오케스트레이터 | `codex queue`: "T01 done" | `results/T01.md`: 변경 파일, 테스트 결과, 막힌 점 |
| 재지시 | `cmux send` 한 줄 | `tasks/T01-retry1.md`: 원래 지시와 부족한 점 |

재시도할 때는 결과를 덮어쓰지 않고 새 파일을 만든다. 오케스트레이터가 무엇을 잡아냈는지 비교할 이력이 실험의 핵심 산출물이기 때문이다.

### 단계

1. **준비**: `run-id`를 생성하고 `devlifeteam/<run-id>/`를 만든다. 워커 pane(`title: "Worker"`)을 `claude --agent devlife-worker`로 띄우고, 사이드바를 "준비"로 표시한다.
2. **문서**: `plan-creator` 또는 `spec-creator`로 사람과 대화하며 작성한다.
3. **승인**: 명시적 승인을 받은 뒤 문서의 작업들을 `ledger.md`로 옮긴다(T01..Tn).
4. **루프** (작업마다):
   1. 워커에 `/clear`를 전송한다.
   2. `tasks/Txx.md`를 작성한다.
   3. 워커에 한 줄 지시를 전송한다.
   4. 워커가 작업한 뒤 `results/Txx.md`를 쓰고 `codex queue`로 알린다.
   5. 오케스트레이터가 결과를 읽고 테스트를 직접 실행해 완료 조건을 검증한다.
   6. 통과하면 원장을 갱신하고 사이드바 진행률을 올린다. 미달이면 부족한 점을 적은 재지시 파일로 다시 보낸다(최대 2회).
5. **보고**: 전체 완료 또는 막힘 시 cmux 알림을 보내고, 오케스트레이터 pane에 결과를 보고한다.

## 에러 처리

| 실패 | 감지 | 대응 |
|---|---|---|
| 테스트 실패, 완료 조건 미달 | 오케스트레이터 검증 | 부족한 점을 적어 재지시. 2회 초과 시 사람에게 보고하고 대기 |
| 워커가 스스로 막힘 | 결과 파일의 "막힌 점" | 오케스트레이터가 재지시할지 사람에게 보고할지 판단 |
| 워커 무응답 (권한 프롬프트 멈춤 등) | 알림 타임아웃 | 워커 pane 화면을 읽고 원인을 포함해 사람에게 보고 |
| 워커 pane 소실 | pane 탐색 실패 | pane을 다시 띄우고 현재 작업 재지시 |
| 오케스트레이터 컨텍스트 압축, 세션 중단 | — | `ledger.md` 기준으로 이어서 진행 |

## 기존 자산과의 관계

비즈니스 도메인 로직이 없는 하네스라 도메인 모델은 해당 없다. 대신 레포의 기존 자산과 맞닿는 지점은 다음과 같다.

- **배포 구조**: Codex 플러그인(`codex/.codex-plugin`)에 오케스트레이터 스킬이, Claude 플러그인(루트 `.claude-plugin`)에 워커 에이전트가 들어간다. 사용자는 두 플러그인을 모두 설치해야 한다.
- **`cmux` 스킬**: `skills/`(v0.3.0)와 `codex/skills/`(v0.2.0)가 갈라져 있어 parity 검사에서 제외된 상태다. 오케스트레이터는 Codex 쪽(v0.2.0)을 사용한다.
- **`codex/AGENTS.md`의 피드백·계획 규칙**: 문서 작성 단계에서는 사람과 대화하므로 그대로 적용된다. 승인 이후 루프에서는 정책이 우선한다.
- **`scripts/check-skill-parity.sh`**: `skills/`에 짝이 없는 Codex 전용 스킬을 어떻게 처리하는지 확인이 필요하다. 필요하면 예외 목록에 추가한다.
- **기존 스킬 영향**: `devlife-codex`, `devlife-team-starter`, `spec-creator`, `plan-creator`는 수정하지 않는다.

## 검증 전략

스킬과 에이전트 정의라 자동 테스트 대상이 없으므로 실험과 시나리오 실행으로 검증한다.

**선행 확인 실험** (구현 전):

| # | 확인 항목 | 실패 시 |
|---|---|---|
| 1 | `codex queue`가 실행 중인 TUI 세션에서 새 턴을 시작시키는지 | 결과 파일 폴링으로 대체 |
| 2 | 오케스트레이터가 자기 세션 ID나 이름을 알 수 있는지 | 1과 함께 폴링으로 대체 |
| 3 | `--agent` 실행 시 전역 CLAUDE.md가 로드되는지, 충돌 시 어느 쪽이 우선하는지 | 워커 규칙을 지시 파일에도 명시 |
| 4 | 플러그인 에이전트를 `--agent`로 부를 때 네임스페이스가 붙는지 | 런처 명령의 에이전트 이름 조정 |

1~3이 모두 실패해 상주 pane 방식이 불안정하면, 워커를 작업마다 `claude -p --agent devlife-worker --output-format json`으로 실행하는 방식으로 전환한다. 인계 프로토콜과 워커 에이전트는 그대로 쓰고, 워커 실행 방식만 바뀐다.

**시나리오**:
- 작업 2개짜리 plan 정상 완료
- 테스트 실패 후 재지시로 성공
- 재시도 상한 도달 후 사람에게 보고
- 워커 무응답 타임아웃 보고
- 루프 중간 중단 후 `ledger.md`로 재개
- spec 경로: 하위 작업별 plan 승인이 반복되는지
