# plan-creator

단일 태스크의 구현 계획 문서를 작성합니다.  
API 설계, 비즈니스 로직, 구현 파일 목록, TDD 테스트 순서까지 포함한 상세 계획을 생성합니다.

## 언제 사용하나요?

- 새 기능이나 버그 픽스 구현을 시작하기 전
- API 설계, 비즈니스 로직 흐름을 미리 정리하고 싶을 때
- TDD로 개발할 테스트 케이스 목록이 필요할 때
- `spec-creator`로 분해한 하위 태스크를 구체화할 때

## 트리거 문구

```
"계획 작성해줘"
"계획을 md 파일에 작성해줘"
"구현 계획"
"실행 계획"
"계획 MD로 정리"
```

## 실행 흐름

0. **요구사항 문서 읽기 (선택)** — 스펙·설계 문서·티켓이 주어지면 먼저 읽고 도메인 문맥·불변성·범위는 그대로 받음. 문서가 여러 작업을 담고 있는데 요청이 지목하지 않으면 탐색 전에 묻고, 코드가 문서와 어긋나면 2단계에서 물음
1. **코드베이스 탐색** — 요청이 지목한 대상을 포함하는 **가장 좁은 범위**에서 Explore 서브에이전트 실행, **8개 카테고리 전부 요청**(카테고리당 상위 8개 상한), 결과가 경계에 닿으면 범위를 넓혀 재실행
2. **명확화 질문** — 열린 쟁점이 닫힐 때까지 (사전 개수 없음) + **모순 검사** (범위/리스크/기술/일정). 코드·프로젝트 규칙으로 정해지지 않는 **새 파일 배치**와, 기존 코드 수정 시 **목표 구조 후보**, **기존 구현과의 분리**도 질문 대상. 질문은 핵심과 이유만 한 문장씩
3. **계획 문서 작성** — `docs/plan/task-{feature}.md` 생성 (디렉토리 없으면 생성)
4. **자체 검증 7항목 + 피드백 요청** — 검증 결과와 `[코드추론]` 불변성을 함께 보고, 사용자 결정이 필요한 항목이 있으면 핸드오프 차단 (섹션 7 질문은 막지 않음)
5. **TDD 스킬로 넘김** — 승인되면 `tdd-subagent`(순차) / `tdd-agent-team`(병렬 팀) 중 하나를 골라 계획 문서를 입력으로 바로 구현을 시작하거나 여기서 마침

### 탐색 범위 — 좁게 시작해서 넓힌다

**목적**: 계획의 근거를 코드에서 찾음 — 새 코드가 들어갈 패키지·클래스, 비즈니스 불변성, 재사용할 코드, 따라 하면 안 되는 결함, (기존 코드 수정 시) 정비. 코드로 정할 수 없는 것은 2단계 질문으로 넘김

**범위는 필요할 때 넓히고, 카테고리 목록은 줄이지 않습니다.**

- 범위: 대상 파일과 직접 호출부 → 패키지 → 도메인 순. 탐색 결과가 컨텍스트 창을 가장 많이 차지하므로 좁게 시작하고, 좁게 잡아 틀리면 비용은 **탐색 한 번 더**
- 카테고리: 6번 생략 예외 하나만 빼고 항상 전부 요청 (요구사항 문서가 불변성을 이미 정했으면 6번 생략 — 재도출해도 더 약한 `[코드추론]` 근거만 남음). 빠진 카테고리는 **결과에 흔적이 없어 나중에 알 수 없는 사각지대**

아래가 나오면 범위를 한 단계 넓혀 다시 훑고, 더 나오지 않으면 그만 넓힙니다.

- 현재 범위 밖의 코드가 대상 코드를 호출함 — 다른 도메인, 요청에 없던 애그리거트
- 변경이 지켜야 할 가드 절·검증 애노테이션·enum 전이가 있는데, 그 이유가 현재 범위 안에서 보이지 않음
- 이번 변경이 참조하는 구현의 결함이 범위 경계에 걸쳐 일부만 보임

### 탐색 카테고리

| # | 카테고리 | 쓰이는 곳 |
|---|---------|----------|
| 1 | 진입점 — HTTP 요청·스케줄·메시지·이벤트 같은 외부 트리거를 받는 코드 전부 (예: 컨트롤러, 배치 작업, 메시지 리스너). 트리거, 시그니처, 진입점·호출 클래스의 패키지 경로 | 배치 스캔, 섹션 6 |
| 2 | 현재 범위의 서비스 — 클래스명·public 시그니처 | 재사용 스캔 |
| 3 | 도메인 모델/엔티티 — 클래스명·변경과 관련된 필드·enum | 섹션 2 |
| 4 | "id로 조회하고 없으면 예외"를 이미 감싼 클래스 (예: `ReadService`) | 재사용 스캔, 섹션 6 스니핏 |
| 5 | 현재 범위에서 던지는 예외 클래스와 던지는 위치 | 섹션 6 스니핏 |
| 6 | 비즈니스 제약을 드러내는 검증 애노테이션·가드 절 | 섹션 2 불변성 |
| 7 | 이번 요구사항이 건드리는 동작을 이미 검증하는 테스트 | 섹션 8 `[REGRESSION]` |
| 8 | **이번 요구사항이 참조할 기존 구현의 결함** — 예: 페이징·오프셋 계산, 경계값(날짜·시간 정밀도), 인덱스를 못 타는 조인, 중복 조건, 필터를 조용히 흘리는 분기. 각각 *무엇을 하는지*와 *왜 틀렸는지*를 함께 | 함정 스캔, 섹션 3 |

- **카테고리당 상위 8개 상한** — 초과분은 나열하지 않고 `+N more`로만 보고
- 탐색 프롬프트 첫 줄에 **요구사항**을 주고, 결과는 경로·시그니처만. **8번만 예외**로 결함마다 `경로:라인`·동작·틀린 이유를 한두 문장
- 탐색 후 카테고리 3·6 중 **변경이 수정하거나 호출하는 파일은 모두** 직접 읽어 불변성 파악 (보통 2~3개, 그 밖은 읽지 않음)
- 7번은 도메인 테스트 목록이 아니라 **겹치는 동작을 검증하는 것만** — 용도가 `[NEW]`/`[REGRESSION]` 태깅이기 때문
- **8번이 브라운필드 인접 작업에서 계획의 값어치를 만듭니다**

### 섹션 생략 기준

템플릿은 **코드 작업에만** 씁니다. 코드 작업 외(런북, 문서, 조사)에는 작업에 맞는 구성으로 쓰고, 템플릿 섹션 기준의 자체 검증과 TDD 인계는 적용하지 않습니다.

코드 작업의 템플릿 섹션은 **Step 1·2가 아무것도 내놓지 못했을 때만** 생략합니다 — 예: 엔드포인트가 없는 변경의 섹션 4. 조사하지 않아서 빠진 섹션이 바로 이 규칙이 막으려는 사각지대입니다.

- **생략하지 않는 섹션**: 섹션 3, 기존 코드 수정 시 섹션 0 — 적을 것이 없으면 `해당 없음`
- **섹션 7**: 위험(장애 양상, 규모)과, 답에 따라 섹션 6·8이 바뀌는 질문만. 기존 동작을 따른 선택은 "기존 동작을 따름" 아래에 한 번만

### 함정 스캔 (재사용 스캔의 역방향)

**목적**: 기존 결함을 새 코드가 따라 하지 않게 함. AI는 기존 코드를 정답으로 여기므로, 적지 않은 결함은 다시 배포됩니다.

- 탐색 8번 결과 + 직접 읽은 파일에서, **새 코드가 따라 쓰거나 호출할 코드의 결함만** 남깁니다
- 각 항목은 진단으로 끝내지 않고 **`→ 신규는`** 결정까지 씁니다
- 항목 형식: `현재 코드`(위치마다 한 줄) → `왜 문제인가` → 조건 표(입력에 따라 결과가 틀릴 때만) → `→ 신규는`(지시가 여러 개면 번호 목록) → `기존 코드`(고칠지·분리할지 + 이유 한 문장). 요약 표는 두지 않습니다
- 남는 것이 없으면 `해당 없음`

### 문장 규칙

**목적**: 계획은 코딩 단계마다 다시 읽히므로, 문장마다 한 번 읽고 이해되게 씁니다.

모든 계획:
- 한 문장에는 사실 하나만 씁니다. `~지만`, `~며`, `~고`, `그래서`로 잇지 않습니다
- 괄호로 덧붙이지 않습니다. 코드 식별자, 값, `3-x` 참조는 괄호에 써도 됩니다
- `적절히`, `필요 시`, `등`, `관련`, `처리한다` 같은 모호한 말은 값, 조건, 이름으로 바꿉니다. 모르면 사용자에게 묻습니다
- `기본적으로`, `참고로`, `~하는 것이 좋다` 같은 군더더기는 뺍니다

코드 작업 템플릿:
- 표 셀은 결정 한 문장에 이유 한 문장까지만 씁니다. 절차는 섹션 5에 두고 참조합니다
- 섹션 2 불변성은 규칙 최대 두 문장, 위반 시 결과 한 문장으로 씁니다
- 섹션 3 항목의 `왜 문제인가`와 `기존 코드`의 이유(고칠지, 분리할지)는 빼지 않고 각각 한 문장으로 씁니다

### 배치 스캔 (새 클래스를 추가할 때)

**목적**: 새 클래스를 프로젝트가 같은 종류의 클래스를 두는 곳에 둠. 새 클래스마다 **같은 도메인에서 같은 역할을 하는 기존 클래스의 위치**를 탐색 1번 결과로 확인하고, 그 위치를 기본값으로 둡니다.

- 기존 위치를 따르면 → 질문 없이 진행
- 다른 위치에 두려 하거나, 도메인이 이미 여러 위치에 흩어져 있으면 → **명확화 질문**으로
- 기존 위치가 없으면 → CLAUDE.md 같은 프로젝트 문서의 구조 규칙을 따르고, 규칙이 없으면 질문

### 불변성 출처 태그

섹션 2의 각 불변성에는 출처 태그를 붙입니다. 불변성 ID는 붙이지 않습니다. TDD 스킬(`tdd-subagent`·`tdd-agent-team`)이 불변성을 가져갈 때 직접 번호를 매깁니다.

Step 1 코드의 enum 상태 전이, 검증 애노테이션, 가드 절에서 뽑은 불변성은 `[코드추론]`입니다. `[사용자확인]`은 이번 대화에서 사용자가 실제로 답한 경우에만 붙입니다. 답이 없으면 코드에서 뽑은 불변성은 `[코드추론]`으로 두고, 그 밖의 불변성은 빼고 질문을 섹션 7에 적습니다. 자체 검증 6번에서 이를 확인합니다.

| 출처 | 의미 | 검토 우선순위 |
|------|------|-------------|
| `[문서]` | 요구사항 문서에 적힌 그대로 | 가장 낮음 |
| `[사용자확인]` | 2단계에서 사용자가 답함 | 낮음 |
| `[코드추론]` | Step 1 코드에서 읽음. 이유는 확인되지 않음 | **가장 높음 — 4단계 보고에서 따로 나열** |

**격리 불변성** — 목적: 신규 코드와 기존 코드가 서로의 테이블을 읽거나 쓰는 것을 테스트로 잡음. 테이블을 나눠도, 두 테이블을 함께 읽는 쿼리나 한쪽 저장이 다른 쪽 테이블을 바꾸는 이벤트가 하나라도 있으면 분리가 깨집니다. 같은 기능의 기존 구현이 운영 중이고 새 구현은 별도 테이블을 쓴다면, 분리 여부를 2단계에서 묻습니다. 요구사항 문서가 정했으면 묻지 않습니다. 문서나 사용자 답이 분리를 정했을 때만 "신규 코드는 기존 테이블을 읽거나 쓰지 않는다"와 그 역방향을 불변성으로 적습니다.

### 목표 구조 정하기 (섹션 0, 기존 코드 수정 시)

**목적**: 이번 요구사항을 쉽게 넣게 해 주는 정비를 찾음. 요구사항이 건드리지 않는 스멜은 후보가 아님. 후보는 명확화 질문으로, 사용자가 고른 것이 섹션 0

목표 구조는 **기존 분기를 고치지 않고 클래스·메서드·필드 추가만으로 요구사항이 들어가는 구조**입니다.

1. **목표 구조** — 위 기준에 맞는 구조를 먼저 그림
2. **Tidy First** — 기존 코드를 목표 구조로 옮깁니다. 동작은 바꾸지 않습니다 (`refactor` 커밋)
3. **본 작업** — 목표 구조 위에 요구사항을 추가합니다 (`feat` 커밋)

아래 모양은 예시입니다. 맞는 것이 없으면 다른 모양을 씁니다.

| 요구사항이 추가하는 것 | 목표 형태 | 요구사항은 |
|---|---|---|
| 기존 분기 항목(타입·채널·정책)의 새 케이스 | 기존 케이스를 한 추상화의 구현체로 | 새 클래스 |
| 기존 개념에 대한 새 규칙 | 규칙의 데이터와 동작을 한 도메인 객체로 | 그 객체의 메서드·가드 |
| 흐름의 새 단계 | 흐름을 이름 있는 단계로 분리 | 메서드 하나 |
| 새 입력값 | 흩어진 파라미터를 한 객체로 | 그 객체의 필드 |

- **기존 설계 안에서 정비** — 같은 계층·패키지·패턴. 설계 변경은 섹션 7에 별도 작업으로. 정비 대상의 호출부는 이번 범위 안
- **쉬워지는 정도와 늘어나는 복잡도를 함께 따짐** — 추상화는 이번 요구사항이 그 분기에 케이스를 추가할 때만. 구현체 1개뿐인 인터페이스는 만들지 않음
- **후보** — 지금 구조에 더해 요구사항을 쉽게 만드는 정비안 전부. 영향 범위가 겹치면 하나로 합침. 정비 내용·기법, 영향 범위, 기능 작업이 더할 것을 적음. 정비 코드에 기존 테스트가 없으면 영향 범위에 필요한 특성화 테스트를 적고 명확화 질문에서 사용자가 고름
- **이미 추가만으로 들어가면** — 질문 없이 `해당 없음`과 이유 한 문장

```
task-{feature}.md
├── 0. 코드 구조 정비 (Tidy First)  ← 기존 코드 수정 시 항상 포함 (없으면 "해당 없음 — 이유")
├── 1. Feature Overview
├── 2. Domain Context & Invariants (출처 태그, 격리 불변성 포함)
├── 3. 기존 코드의 함정 (답습 금지)   ← 없으면 "해당 없음"
├── 4. API Design        ← 엔드포인트별 Request/Response 예시
├── 5. Business Logic
├── 6. Implementation Files + 코드 스니핏  ← 메서드 본문까지 포함
├── 7. Considerations & Questions
├── 8. Implementation Order (TDD 순서)
└── 9. Acceptance Criteria
```

## 파일명 규칙

| 상황 | 파일명 |
|------|--------|
| 사용자가 파일명 지정 | 지정한 이름 그대로 사용 |
| 지정 없음 | `task-{feature}.md` (예: `task-payment-refund.md`) |

## 워크플로우 위치

```
devlife-brainstorming
└── spec-creator
    └── plan-creator  ← 현재 위치
        └── tdd-subagent / tdd-agent-team
```

## 관련 스킬

- [spec-creator](./spec-creator.md) — plan-creator 실행 전 Spec 문서 작성
- [tdd-subagent](./tdd-subagent.md) — 계획 문서를 입력으로 TDD 사이클을 순차 실행
- [tdd-agent-team](./tdd-agent-team.md) — 계획 문서를 입력으로 RED·GREEN 팀원이 병렬 실행
