# plan-creator

단일 태스크의 구현 계획 문서를 작성합니다.  
API 설계, 비즈니스 로직, 구현 파일 목록, TDD 테스트 순서까지 포함한 상세 계획을 생성합니다.

## 언제 사용하나요?

- 새 기능이나 버그 픽스 구현을 시작하기 전
- API 설계, 비즈니스 로직 흐름을 미리 정리하고 싶을 때
- TDD로 개발할 테스트 케이스 목록이 필요할 때
- `prd-creator`로 만든 하위 태스크를 구체화할 때

## 트리거 문구

```
"계획 작성해줘"
"계획을 md 파일에 작성해줘"
"구현 계획"
"실행 계획"
"계획 MD로 정리"
```

## 실행 흐름

0. **범위·깊이 판정** — Brownfield/Greenfield 구분 + Minimal/Standard/Comprehensive 선택 후 사용자 확인
1. **코드베이스 탐색** — 깊이에 따라 요청 카테고리를 골라 Explore 서브에이전트 실행 (아래 표), 카테고리당 상위 8개 상한
2. **명확화 질문** — 깊이별 질문 수 목표 + **모순 검사** (범위/리스크/기술/일정)
3. **계획 문서 작성** — `docs/plan/task-{feature}.md` 생성 (디렉토리 없으면 생성)
4. **자체 검증 6항목 + 피드백 요청** — 검증 결과를 함께 보고, 미해결 항목이 있으면 핸드오프 차단

### 깊이 3단계

작업 성격에 따라 실행 범위가 달라집니다. 자동 판정하지 않고 **결과를 명시해 확인받은 뒤** 진행합니다.

| 깊이 | 적합한 작업 | 코드 탐색 | 질문 수 | 생략 섹션 |
|------|-----------|---------|--------|---------|
| Minimal | 버그 수정, 동작 보존 리팩터링 | 대상 파일 + 직접 호출부 | 2~4 | 3(API), 4(로직), 6(고려사항) |
| Standard | 신규 기능, 기존 기능 확장 | 전체 Explore | 5~8 | 없음 |
| Comprehensive | 신규 모듈, 크로스커팅 변경 | 전체 Explore + 애그리거트 정독 | 8~12 | 없음 (6에 리스크 추가) |

### 탐색 범위 (깊이별)

탐색 결과는 이 스킬에서 컨텍스트로 들어오는 **가장 큰 단일 항목**이라, 깊이에 따라 요청 카테고리를 줄입니다.

| # | 카테고리 | Minimal | Standard | Comprehensive |
|---|---------|:-------:|:--------:|:-------------:|
| 1 | 컨트롤러 — 경로·엔드포인트 애노테이션·시그니처 | ● | ● | ● |
| 2 | 동일 도메인 서비스 — 클래스명·public 시그니처 | ● | ● | ● |
| 3 | 도메인 모델/엔티티 — 클래스명·주요 필드·enum | | ● | ● |
| 4 | ReadService에 캡슐화된 `find-by-id + throw` 패턴 | | ● | ● |
| 5 | 관련 예외 클래스와 발생 지점 | | ● | ● |
| 6 | 비즈니스 제약을 암시하는 검증 애노테이션·가드 절 | | ● | ● |
| 7 | 이번 요구사항이 건드리는 동작을 이미 검증하는 테스트 | ● | ● | ● |

- **카테고리당 상위 8개 상한** — 초과분은 나열하지 않고 `+N more`로만 보고
- **Minimal**은 도메인이 아니라 대상 파일 + 직접 호출부가 범위
- 스펙 문서가 불변성을 이미 확정했으면 **6번 생략** (가드 절에서 재도출하면 스펙이 정한 걸 다시 하는 셈이고, 근거 등급도 `[코드추론]`으로 낮아짐)
- 7번은 도메인 테스트 목록이 아니라 **겹치는 동작을 검증하는 것만** — 용도가 `[NEW]`/`[REGRESSION]` 태깅이기 때문

### 불변성 ID와 출처 태그

섹션 2의 각 불변성에는 고정 ID(`INV-001`)와 출처 태그를 부여합니다.
섹션 7은 ID를 참조하고, tdd-team이 같은 ID를 그대로 이어받아 최종 커버리지를 대조합니다.

| 출처 | 의미 | 검토 우선순위 |
|------|------|-------------|
| `[문서]` | 스펙·티켓에 명시됨 | 낮음 |
| `[사용자확인]` | 질문 단계에서 답변받음 | 낮음 |
| `[코드추론]` | 가드 절·enum에서 읽어냄, 이유 미확인 | **가장 높음 — 사용자에게 명시** |

### 변화 지점 추상화 제안

기존 코드를 수정하는 태스크에서는, 요구사항이 건드리는 축이 **앞으로도 계속 늘어나는 축**인지 확인해 추상화를 제안합니다.
탐색 대상은 enum·타입·채널 기준 `if`/`switch` 분기, 하드코딩된 정책값, 한 단계만 다른 중복 메서드 등입니다.

억지 추상화를 막는 기준(**two-case rule**):

| 조건 | 처리 |
|------|------|
| 구체 케이스가 이미 2개 이상 | 추상화 제안 |
| 이번 요구사항이 두 번째 케이스를 추가 | 추상화 제안 |
| 케이스가 1개 | 제안하지 않음 (구현체 1개뿐인 인터페이스는 안티패턴) |
| 도메인 근거 없이 구조 냄새만 있음 | 제안하지 않음 |
| 해당 변화 지점 없음 | `0-2. 추상화 제안`에 `해당 없음` |

제안된 추상화는 설계 결정이므로 **승인 전까지 적용 여부를 확정하지 않으며**, 반려되면 문서에서 삭제합니다.
승인된 경우 기존 케이스로 먼저 추출(`refactor` 커밋)한 뒤, 새 케이스를 기능 커밋(`feat`)에서 구현합니다.

## 생성 문서 구조

```
task-{feature}.md
├── 0. 코드 구조 정비     ← 기존 코드 수정 시에만 포함
│   ├── 0-1. Tidy First      ← 동작 변경 없는 정비
│   └── 0-2. 추상화 제안      ← 변화 지점 (없으면 "해당 없음")
├── 1. Feature Overview
├── 2. Domain Context & Invariants (ID + 출처 태그)
├── 3. API Design        ← 엔드포인트별 Request/Response 예시
├── 4. Business Logic
├── 5. Implementation Files + 코드 스니핏
├── 6. Considerations & Questions
├── 7. Implementation Order (TDD 순서, INV-ID 참조)
└── 8. Acceptance Criteria
```

## 파일명 규칙

| 상황 | 파일명 |
|------|--------|
| 사용자가 파일명 지정 | 지정한 이름 그대로 사용 |
| 지정 없음 | `task-{feature}.md` (예: `task-payment-refund.md`) |
