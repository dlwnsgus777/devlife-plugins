# plan-creator

단일 태스크의 구현 계획 문서를 작성합니다.  
API 설계, 비즈니스 로직, 구현 파일 목록, TDD 테스트 순서까지 포함한 상세 계획을 생성합니다.

## 언제 사용하나요?

- 새 기능이나 버그 픽스 구현을 시작하기 전
- API 설계, 비즈니스 로직 흐름을 미리 정리하고 싶을 때
- TDD로 개발할 테스트 케이스 목록이 필요할 때
- `spec-creator`로 분해한 하위 태스크를 구체화할 때

## 트리거 문구

```
"계획 작성해줘"
"계획을 md 파일에 작성해줘"
"구현 계획"
"실행 계획"
"계획 MD로 정리"
```

## 실행 흐름

1. **코드베이스 탐색** — 요청이 지목한 대상을 포함하는 **가장 좁은 범위**에서 Explore 서브에이전트 실행, **8개 카테고리 전부 요청**(카테고리당 상위 8개 상한), 결과가 경계에 닿으면 범위를 넓혀 재실행
2. **명확화 질문** — 열린 쟁점이 닫힐 때까지 (사전 개수 없음) + **모순 검사** (범위/리스크/기술/일정). 코드·프로젝트 규칙으로 정해지지 않는 **새 파일 배치**와, 기존 코드 수정 시 **목표 구조 후보**도 질문 대상
3. **계획 문서 작성** — `docs/plan/task-{feature}.md` 생성 (디렉토리 없으면 생성)
4. **자체 검증 7항목 + 피드백 요청** — 검증 결과를 함께 보고, 미해결 항목이 있으면 핸드오프 차단
5. **TDD 스킬로 넘김** — 승인되면 `tdd-subagent`(순차) / `tdd-agent-team`(병렬 팀) 중 하나를 골라 계획 문서를 입력으로 바로 구현을 시작하거나 여기서 마침

### 탐색 범위 — 좁게 시작해서 넓힌다

탐색 결과는 이 스킬에서 컨텍스트로 들어오는 **가장 큰 단일 항목**이라 범위를 좁혀야 하지만, 범위는 코드를 보기 전에는 정확히 알 수 없습니다. 그래서 **범위는 잠정, 카테고리 목록은 고정**입니다.

- 좁게 잡아 틀리면 비용은 **탐색 한 번 더**
- 카테고리를 빼고 틀리면 **필요했다는 사실조차 알 수 없는 사각지대**

비대칭이 명확하므로, 요청이 지목한 대상을 포함하는 가장 좁은 범위에서 시작하고 아래가 나오면 넓혀 다시 훑습니다.

- 가정한 범위 밖의 호출부 — 다른 도메인, 요청에 없던 애그리거트
- 변경이 만족시켜야 할 가드 절·검증 애노테이션·enum 전이인데, 현재 범위로는 그 이유가 설명되지 않는 경우
- 이번 변경이 참조하는 구현의 결함이 탐색 경계에 걸쳐 있는 경우

넓힐 때는 한 줄로 알리고 계속 진행합니다.

### 탐색 카테고리

범위와 무관하게 **8개 카테고리를 항상 전부 요청**합니다.

| # | 카테고리 |
|---|---------|
| 1 | 컨트롤러 — 경로·엔드포인트 애노테이션·시그니처, 컨트롤러와 호출 클래스의 패키지 경로 |
| 2 | 동일 도메인 서비스 — 클래스명·public 시그니처 |
| 3 | 도메인 모델/엔티티 — 클래스명·주요 필드·enum |
| 4 | ReadService에 캡슐화된 `find-by-id + throw` 패턴 |
| 5 | 관련 예외 클래스와 발생 지점 |
| 6 | 비즈니스 제약을 암시하는 검증 애노테이션·가드 절 |
| 7 | 이번 요구사항이 건드리는 동작을 이미 검증하는 테스트 |
| 8 | **이번 요구사항이 참조할 기존 구현의 알려진 결함** — 페이징·오프셋 계산, 경계값(날짜·시간 정밀도), 인덱스를 못 타는 조인, 중복 조건, 필터를 조용히 흘리는 분기. 각각 *무엇을 하는지*와 *왜 틀렸는지*를 함께 |

- **카테고리당 상위 8개 상한** — 초과분은 나열하지 않고 `+N more`로만 보고
- 유일한 생략 규칙은 **근거 기반**: 스펙 문서가 불변성을 이미 확정했으면 **6번 생략** (가드 절에서 재도출하면 스펙이 정한 걸 다시 하는 셈이고, 근거 등급도 `[코드추론]`으로 낮아짐)
- 7번은 도메인 테스트 목록이 아니라 **겹치는 동작을 검증하는 것만** — 용도가 `[NEW]`/`[REGRESSION]` 태깅이기 때문
- **8번이 브라운필드 인접 작업에서 계획의 값어치를 만듭니다**

### 섹션 생략 기준

템플릿 섹션은 **Step 1·2가 아무것도 내놓지 못했을 때만** 생략합니다 — 변경에 엔드포인트가 없으면 섹션 4 없음, 참조 구현에 결함이 없으면 섹션 3은 `해당 없음`. 조사하지 않아서 빠진 섹션이 바로 이 규칙이 막으려는 사각지대입니다.

### 함정 스캔 (재사용 스캔의 역방향)

재사용 스캔이 "무엇에 기댈 것인가"를 묻는다면, 함정 스캔은 **"무엇을 따라 하지 말 것인가"**를 묻습니다.
AI는 기존 코드를 이 프로젝트의 정답으로 읽고 결함까지 그대로 복제하므로, 발견하고도 적지 않은 결함은 다시 출고됩니다.

- 탐색 8번 결과 + 직접 읽은 2~3개 파일에서, **신규 코드가 모방으로 물려받을 결함만** 남깁니다 — 코드베이스 무관한 구석의 결함은 이 계획의 일이 아닙니다
- 각 항목은 진단으로 끝내지 않고 **`→ 신규는`** 결정까지 씁니다
- 항목 형식: `현재 코드`(위치마다 한 줄) → `왜 문제인가` → 조건 표 → `→ 신규는`(지시가 여러 개면 번호 목록) → `기존 코드`(고칠지·분리할지 + 이유 한 문장). 요약 표는 두지 않습니다
- 남는 것이 없으면 `해당 없음`

### 문장 규칙

계획 문서가 장황해지는 원인은 섹션 수가 아니라 문장 모양입니다.

- 한 문장에는 사실 하나만 씁니다. `~지만`, `~며`, `~고`, `그래서`로 잇지 않습니다
- 괄호로 덧붙이지 않습니다. 코드 식별자, 값, `3-x` 참조는 괄호에 써도 됩니다
- 표 셀은 결정 한 문장에 이유 한 문장까지만 씁니다. 절차는 섹션 5에 두고 참조합니다
- 불변성은 규칙 문장 2개까지 쓰고, 위반 시 영향은 한 문장으로 씁니다
- 위반 시 영향, `왜 문제인가`, 고칠지·분리할지의 이유는 빼지 않고 한 문장으로 줄입니다
- 다른 섹션에 있는 사실은 다시 쓰지 않고 섹션을 참조합니다
- 줄이려고 사실을 지우지 않습니다. 다른 곳에 이미 있는 내용만 지웁니다

### 배치 점검 (새 클래스를 추가할 때)

새 파일마다 **같은 기능에서 같은 역할을 하는 기존 클래스가 어디에 있는지**를 탐색 1번 결과로 확인하고, 그 위치를 기본값으로 둡니다. 패키지 구조는 프로젝트마다 다르므로 가정하지 않고 탐색 결과에서 읽습니다.

- 기존 위치를 따르면 → 질문 없이 진행
- 다른 위치에 두려 하거나, 기능이 이미 여러 위치에 흩어져 있으면 → 섹션 6에서 확정하지 않고 **명확화 질문**으로
- 기존 위치가 없는 신규 기능 → 프로젝트의 문서화된 배치 규칙을 따르고, 규칙이 없으면 질문

### 불변성 출처 태그

섹션 2의 각 불변성에는 출처 태그를 붙입니다. 불변성 ID는 붙이지 않습니다. TDD 스킬(`tdd-subagent`·`tdd-agent-team`)이 불변성을 가져갈 때 직접 번호를 매깁니다.

| 출처 | 의미 | 검토 우선순위 |
|------|------|-------------|
| `[문서]` | 스펙·티켓에 명시됨 | 낮음 |
| `[사용자확인]` | 질문 단계에서 답변받음 | 낮음 |
| `[코드추론]` | 가드 절·enum에서 읽어냄, 이유 미확인 | **가장 높음 — 사용자에게 명시** |

**격리 불변성** — 기존 구현과 나란히 도는 신규 구현(별도 테이블·별도 플로우, 레거시는 아직 살아 있음)이라면 분리를 **양방향 불변성**으로 적습니다. 신규가 기존 저장소를 건드리지 않는다, 그리고 기존이 신규를 끌어오지 않는다. 테이블이 다르다는 구조적 분리는 *왜 성립하는지에 대한 논거*일 뿐 성립한다는 증거가 아니며, 공유 쿼리 하나나 연쇄 사이드 이펙트 하나로 똑같이 깨집니다. 산문이 아니라 불변성으로 적는 이유는 TDD 스킬이 불변성을 받아 양쪽 경계를 각각 테스트하기 때문입니다 — 여기 적어야 주장이 아니라 검증이 됩니다.

### 목표 구조 정하기 (섹션 0, 기존 코드 수정 시)

요구사항에서 거꾸로 생각합니다. 요구사항이 무리 없이 들어갈 구조를 먼저 그리고, 기존 코드를 그 구조로 옮기는 정비를 끌어냅니다.

1. **목표 구조** — "기존 코드를 어떻게 리팩터링해야 이 요구사항을 쉽게 넣을 수 있는가?"
2. **Tidy First** — 기존 코드를 목표 구조로 옮깁니다. 동작은 바꾸지 않습니다 (`refactor` 커밋)
3. **본 작업** — 목표 구조 위에 요구사항을 추가합니다 (`feat` 커밋)

목표 구조를 그릴 때 참고하는 모양입니다. 정답 목록이 아니라 휴리스틱입니다.

| 요구사항이 추가하는 것 | 자연스럽게 받는 구조 |
|---|---|
| 기존 분기 축(타입·채널·정책)의 새 케이스 | 기존 케이스를 한 추상화의 구현체로 — 새 케이스는 새 클래스 |
| 기존 개념에 대한 새 규칙 | 규칙의 데이터와 동작을 한 도메인 객체로 — 새 규칙은 그 객체의 메서드·가드 |
| 흐름의 새 단계 | 흐름을 이름 있는 단계로 분리 — 새 단계는 메서드 하나 |
| 새 입력값 | 흩어진 파라미터를 한 객체로 |

지키는 기준은 세 가지입니다.

- **기존 틀과 설계를 유지합니다.** 다 뜯어고치면 사이드 이펙트를 예측할 수 없습니다. 레이어·패키지·이미 쓰는 패턴 안에서만 움직이고, 정비가 닿는 호출부는 이번 범위 안에 있어야 합니다
- **쉬운 반영에만 치우치지 않습니다.** 반영이 쉬워지는 정도와 정비가 늘리는 복잡도·위험을 함께 따집니다. 구현체 1개뿐인 인터페이스는 만들지 않습니다
- **혼자 정하지 않습니다.** "지금 구조 그대로"를 포함한 후보 2~3개를 명확화 질문에서 비교해 보여 주고, 추천과 이유를 붙여 사용자가 고르게 합니다

정비할 것이 없으면 `해당 없음`과 지금 구조로 어떻게 반영되는지 한 문장을 적습니다. 섹션 0을 생략하지 않으므로, 검토하고 할 게 없었다는 사실이 남습니다.

## 생성 문서 구조

```
task-{feature}.md
├── 0. 코드 구조 정비 (Tidy First)  ← 기존 코드 수정 시 항상 포함 (없으면 "해당 없음 — 이유")
├── 1. Feature Overview
├── 2. Domain Context & Invariants (출처 태그, 격리 불변성 포함)
├── 3. 기존 코드의 함정 (답습 금지)   ← 없으면 "해당 없음"
├── 4. API Design        ← 엔드포인트별 Request/Response 예시
├── 5. Business Logic
├── 6. Implementation Files + 코드 스니핏  ← 메서드 본문까지 포함
├── 7. Considerations & Questions
├── 8. Implementation Order (TDD 순서)
└── 9. Acceptance Criteria
```

## 파일명 규칙

| 상황 | 파일명 |
|------|--------|
| 사용자가 파일명 지정 | 지정한 이름 그대로 사용 |
| 지정 없음 | `task-{feature}.md` (예: `task-payment-refund.md`) |
