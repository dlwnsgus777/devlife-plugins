TDD Team

overview

순차적인 Agent 호출을 사용해 Red-Green-Refactor 3단계 TDD 사이클을 지휘한다. 각 사이클은 작은 동작 증분 하나를 구현한다.

실행 규칙

Execution Rules

  • 이 스킬보다 상위에 있는 system, developer, 프로젝트 CLAUDE.md 지시를 존중한다.
  • 프로젝트 지시가 각 단계마다 피드백을 요구한다면, 사이클 단위로 지킨다 — 사이클당 한 번, 사이클 리뷰어의 판정 이후에 멈춘다. 피드백 주기를 참고한다.
  • RED, GREEN, REFACTOR, 사이클 리뷰, 최종 리뷰에는 서브에이전트(Agent({ subagent_type: "general-purpose", ... }))를 사용한다. Agent 툴을 쓸 수 없으면 not available이라고 말하고 로컬 실행으로 대체한다.

절차의 크기 맞추기

Right-Size the Ceremony

변경 크기와 무관하게 RED/GREEN 분리는 절대 줄이지 않는다. 이것은 위험도 기반이 아니라 구조적인 장치다. 한 사람이 테스트와 구현을 동시에 쓰면 해피 패스만 덮는 쪽으로 기울게 되는데, 테스트가 요구사항을 압박하는 대신 이미 만들려고 마음먹은 것을 서술하는 데서 끝나기 때문이다. RED는 언제나 GREEN이 어떻게 구현할지 모르는 상태로 돌고, GREEN은 언제나 별도의 디스패치로 돈다. 모든 사이클에서 그렇다.

변경 크기에 따라 줄어드는 것, 즉 당신이 조절할 몫은 다음 두 가지다.

  • 사이클 단위(granularity) — 같은 구현 변경을 공유하는 시나리오들은 하나의 태스크로 묶는다 (Setup 4단계).
  • Final Review 범위 — 변경의 파급 범위가 넓지 않은 한 건드린 클래스만 본다 (Final Review 참고).

에이전트 내부의 모든 결정은 그 에이전트의 몫이다. REFACTOR는 건너뛸지 스스로 정하고, 사이클 리뷰어는 얼마나 깊게 볼지 스스로 정하며, 두 리뷰어 모두 당신이 건넨 테스트 결과에서 무엇을 신뢰할지 스스로 판단한다. 각 규칙은 해당 에이전트의 참조 파일에 들어 있고, 어느 것도 당신이 다시 유도할 대상이 아니다. 당신은 디스패치하고 봉투(envelope)를 읽는다. 당신이라면 다르게 판단했을 것이라는 이유로 에이전트를 다시 디스패치하지 않는다. SKIPPED로 끝난 REFACTOR나 diff만 읽은 리뷰어는 설계된 결과이지 미달이 아니다.

Setup

Setup — 0 ~ 6

0.이어서 하기 또는 새로 시작

무엇보다 먼저 프로젝트 루트의 .tdd-team/session.md를 확인한다 — 정확히 그 경로만, 다른 경로는 보지 않는다. .tdd-team/archive-*/ 디렉터리 안에 있는 session.md는 이미 보관된 세션의 것이며 절대 이어서 하기를 트리거하지 않는다.

파일이 있으면 읽고 다음과 같이 묻는다.

"이전 TDD 세션 기록이 있습니다: {완료}/{전체} 태스크 완료, 마지막 단계 {last_phase}. 이어서 진행할까요, 새로 시작할까요?"

  • 이어서 → .tdd-team/context.md와 .tdd-team/session.md를 있는 그대로 채택한다. Setup 2~6단계는 전부 건너뛴다. 이미 실행된 단계다. status가 DONE이 아닌 첫 행부터, 그 행의 last_phase 다음 단계에서 재개하고, feedback_mode, consecutive_needs_fix, fix_rounds_this_cycle, fix_rounds_total을 파일에서 복원한다. 이 카운터들을 복원하는 것이 이어서 하기의 핵심이다. 0부터 시작하면 이전 세션이 이미 써버린 수정 라운드를 다시 돌게 된다. feedback_mode가 unset이면 주기 질문을 한 적이 없다는 뜻이므로, 재개한 사이클을 게이트로 두고 그 사이클의 리뷰어 판정 후에 — 1번 사이클과 똑같이 — 질문한다.
  • 새로 시작 → 이전 세션을 제외 트리 바깥이 아니라 안쪽에 보관한다. .tdd-team/archive-{YYYYMMDD-HHMMSS}/를 만들고 현재 .tdd-team/에 있는 모든 것을 그 안으로 옮기되, 기존 archive-* 디렉터리들은 그대로 둔다. .tdd-team/ 자체는 남아서 보관본만 담고, Setup 5~6단계가 새 세션의 context.md와 session.md를 그 안에 쓴다. 그런 다음 Setup을 정상적으로 진행한다. 보관본은 절대 삭제하지 않는다 — 이전 세션의 디버깅 기록이다. 형제 경로인 .tdd-team.{YYYYMMDD-HHMMSS}는 .tdd-team/ 제외 항목을 벗어나 사용자 저장소에 추적되지 않는 잔여물을 남긴다. 안쪽에 보관하면 이 스킬이 만드는 모든 파일을 제외 항목 하나로 덮을 수 있다.

파일이 없으면 1단계로 넘어간다.

1.스킬 경로와 산출물 디렉터리 확정

이 SKILL.md는 알려진 절대 경로에서 로드되었다. 그 상위 디렉터리를 SKILL_DIR로 잡는다. 각 단계 에이전트의 프롬프트 파일은 {SKILL_DIR}/references/ 아래에 있고, 해당 단계의 Agent 호출이 직접 읽는다. 여기서 따로 불러올 통합 프롬프트 파일은 없다.

{SKILL_DIR}/references/red-agent.md
{SKILL_DIR}/references/green-agent.md
{SKILL_DIR}/references/refactor-agent.md
{SKILL_DIR}/references/cycle-reviewer.md
{SKILL_DIR}/references/final-reviewer.md
{SKILL_DIR}/references/fix-agent.md

그런 다음 산출물 디렉터리를 정한다. 이 세션이 만드는 모든 파일이 여기에 놓이고, 모든 에이전트가 입력을 여기서 읽는다.

  • TDD_DIR = .tdd-team — 스킬은 프로젝트 루트에서 실행되므로 이 경로는 작업 디렉터리를 기준으로 해석된다
  • TASK_DIR = {TDD_DIR}/task-{NN} — NN은 두 자리로 0을 채운 태스크 번호

TDD_DIR을 만들고 git 추적에서 제외한다.

mkdir -p .tdd-team
git rev-parse --git-dir >/dev/null 2>&1 \
  && ! grep -qxF '.tdd-team/' "$(git rev-parse --git-dir)/info/exclude" 2>/dev/null \
  && echo '.tdd-team/' >> "$(git rev-parse --git-dir)/info/exclude"

.gitignore가 아니라 .git/info/exclude를 쓴다. .gitignore는 사용자 저장소에서 추적되는 파일이고, 이 스킬은 거기에 커밋을 만들지 않는다.

2.환경 탐지

빌드 파일(build.gradle.kts, pom.xml, package.json 등)을 확인하고 테스트 명령을 결정한다. 다음을 잡는다.

PROJECT_ROOT / SOURCE_DIR / TEST_DIR / TEST_CMD / TEST_SCOPED_CMD / TEST_COMPILE_CMD / TEST_FRAMEWORK
  • PROJECT_ROOT — 절대 경로. 당신이 아니라 에이전트를 위해 잡는다. context.md에 들어가서, 디스패치된 에이전트가 추측 없이 경로를 해석할 수 있게 한다.
  • TEST_CMD — 전체 스위트 명령. 기본적으로 실행하지 않는다(Final Review 참고). 사용자가 전체 스위트/클래스 간 회귀 커버리지를 명시적으로 요청할 때만 실행한다.
  • TEST_SCOPED_CMD — 테스트 클래스 하나를 실행하는 명령 템플릿으로, 사이클 내 모든 테스트 실행과 Final Review가 사용한다. Gradle: ./gradlew test --tests "{FQCN}" --offline (JUnit @Nested 클래스는 감싸는 클래스의 FQCN으로 실행한다). Maven: mvn -o test -Dtest={ClassName}. npm/jest/vitest: 테스트 파일 경로를 전달한다(예: npx vitest run {test_file}). 대부분의 프레임워크는 한 번의 호출에서 여러 --tests/파일 경로 인자를 받는다 — 클래스마다 명령을 나누지 말고 이를 이용해 건드린 여러 클래스를 함께 실행한다.
  • TEST_COMPILE_CMD — 아무것도 실행하지 않고 테스트 소스만 컴파일한다. RED는 실제 실행 비용을 치르기 전에 컴파일 오류를 없애는 데 이를 사용한다. 새로 만든 테스트 클래스는 실패하는 데 실패하는 것보다 컴파일에 실패하는 경우가 훨씬 많기 때문이다. Gradle: ./gradlew compileTestJava --offline (Kotlin: compileTestKotlin). Maven: mvn -o test-compile. TypeScript: npx tsc --noEmit. 별도 컴파일 단계가 없는 스택(순수 JS, Python)이라면 none으로 두고 RED는 곧바로 실행으로 넘어간다.

3.도메인 불변성 식별

출처는 요구사항 문서가 먼저이고 코드가 그다음이다. 스펙이든 계획서든 티켓이든 평문 설명이든 모두 같은 방식으로 다룬다.

  1. 문서가 제공됨 → 오직 그 문서에서만 불변성을 도출한다. 아직 코드를 스캔하지 않는다. 문서가 불변성을 명시하고 있다면 적힌 그대로 채택하되, ID(INV-001, …)를 부여하고 있다면 ID까지 포함해 채택한다. 세션 전체에서 그 ID를 그대로 재사용한다. 최종 리뷰어가 계획서를 다시 읽지 않고도 커버리지를 확인하는 수단이다.
  2. 아무것도 제공되지 않음 → "구현할 기능의 요구사항이나 티켓 내용을 공유해주시겠어요?"라고 묻고 기다린다.
  3. 그다음에야 코드(enum 전이, 검증 애너테이션, 가드 절)를 스캔해 문서가 빠뜨린 구조적 제약을 찾는다. 코드가 문서의 의도를 덮어쓰게 두지 않는다.

각 규칙은 코드가 무엇을 하는지가 아니라 무엇이 참이어야 하는지에 대한 서술문으로 표현한다.

"결제 완료 상태로 전환된 주문의 금액은 어떠한 경우에도 변경될 수 없다."

추출한 불변성을 정확히 이 표 형식으로 제시하고, 빠진 것이 없는지 묻는다.

도메인 불변성 (비즈니스 규칙)

  ┌─────┬─────────────────────────────────────────────────────────────────────────────────┐
  │  #  │                                     불변성                                      │
  ├─────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 1   │ {불변성 문장}                                                                   │
  ├─────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 2   │ {불변성 문장}                                                                   │
  └─────┴─────────────────────────────────────────────────────────────────────────────────┘

이 문장들이 테스트 이름의 출처가 된다.

4.TDD 태스크로 분해

문서가 이미 순서가 있는 태스크 목록을 제공한다면 새로 도출하지 말고 그것을 채택한다. [REGRESSION] 태그가 붙은 항목(기존 테스트가 이미 그 동작을 덮고 있음)은 사이클이 아니다. "기존 커버리지로 확인"으로 한 번만 나열하고, 각각에 RED를 주는 대신 Final Review의 일부로 실행한다. [NEW] 항목만 사이클이 된다. 목록을 제시하기 전에 아래의 묶기 규칙과 커버리지 하한을 적용한다. 문서는 가독성을 위해 시나리오를 한 줄에 하나씩 나열하는 경우가 많은데, 그것은 문서의 단위이지 사이클의 단위가 아니다.

각 태스크의 이름은 도메인 규칙 문장으로 짓는다 — RED가 이를 테스트의 @DisplayName으로 바꾼다. 메서드를 어떻게 명명하고, 묶고, 한 문장을 여러 케이스로 나눌지는 red-agent.md의 몫이다. 당신이 줄 것은 문장 하나뿐이다.

같은 구현 변경을 공유하는 시나리오는 묶는다. 사이클은 테스트 메서드 하나가 아니라 구현 작업의 한 단위에 대응해야 한다. 태스크 목록을 확정하기 전에, 같은 가드 절·같은 조건문·같은 작은 함수 하나로 모두 만족되는 시나리오 묶음을 찾는다 — 예를 들어 한 검사의 참/거짓 분기, 또는 하나의 조회에 대한 역할·상태 조합군. 그런 묶음은 시나리오마다 태스크를 만들지 말고, 여러 @DisplayName을 거느린 하나의 태스크로 합친다.

너무 거칠게 묶었다는 신호: GREEN이 작은 변경 하나로 그 태스크의 테스트 메서드 전부를 통과시키지 못한다 — 다시 쪼갠다.

너무 잘게 쪼갰다는 신호: N번 사이클의 RED가 ALREADY_PASSES로 돌아온다. N-1번 사이클의 GREEN이 이미 덮었기 때문이다 — 앞으로는 공유 로직을 실제로 구현하는 이전 태스크에 합친다. 이것은 통제 수단이 아니라 최후의 안전망이다. 모든 태스크 뒤에 있는 변경을 이름 붙이는 사전 점검이 잡았어야 하므로, 이 신호가 울리면 아직 남아 있는 모든 태스크에 대해 그 점검을 다시 돌린다.

커버리지 하한 — 하한이지 상한이 아니다. Setup 3단계의 모든 불변성에는 규칙 안쪽 어딘가의 테스트 하나가 아니라 경계를 고정할 만큼의 테스트가 필요하다. 불변성은 규칙이고, 테스트 하나는 규칙의 한 점만 표본으로 잡을 뿐 어디서 시작하고 끝나는지는 아무것도 증명하지 못한다. 각 불변성의 하한은 다음과 같다.

  • 그것을 위반하는 케이스(규칙이 발동),
  • 그것을 만족하는 가장 가까운 케이스(규칙이 발동하지 않음),
  • 그리고 규칙 자체가 지목하는 모든 추가 상태나 입력 — "결제 완료 상태에서는"이라고 적혀 있다면 결제 대기와 부분 환불은 누가 덧붙인 것이 아니라 규칙이 직접 그은 경계다.

여기에 더해, 이 기능이 건드리는 클래스마다 해피 패스 테스트 하나씩 — 매핑되는 불변성이 없는 곳에도 둔다.

TDD에서 이것은 커버리지 취향의 문제가 아니다. 테스트가 없는 엣지 케이스는 검증되지 않은 동작이 아니라 만들어지지 않은 동작이다. GREEN은 테스트가 요구하는 것만 정확히 구현하고 그 이상은 하지 않기 때문이다. 여기서 테스트를 적게 나열하면 기능이 조용히 덜 만들어진다.

도메인이 이유를 주는 곳에서는 하한을 넘겨도 좋다. 덜어낼 수 있는 시나리오는 언어를 테스트하거나, 프레임워크를 테스트하거나, 단순 접근자를 테스트하는 것뿐이다 — 도메인 규칙의 경계는 절대 아니다. 무언가를 덜어낼 때는 목록을 제시하면서 무엇을 왜 덜어냈는지 말한다.

한 규칙의 경계 케이스들은 같은 가드 절을 공유하므로 묶기 규칙이 이미 그것들을 하나의 태스크에 넣는다 — 한 사이클에 테스트 메서드가 늘어나는 것은 거의 공짜이고 비싼 것은 사이클이 늘어나는 것이며, RED는 같은 규칙에 입력만 다른 케이스들을 스스로 합친다.

목록을 제시하기 전에, 모든 태스크 뒤에 있는 변경을 이름 붙인다. 각 행에 대해 스스로에게 한 줄을 적는다. 어떤 프로덕션 코드 변경이 이 태스크의 테스트를 실패에서 통과로 옮기는가? 그 답이 이것이 사이클인지 아닌지를 결정한다.

  • 구체적인 변경 — 가드 절, 새 메서드, 분기 → 사이클이다.
  • "없음 — 이미 동작한다" → 사이클이 아니라 커버리지다. 그 시나리오들을 해당 로직을 만드는 태스크로 옮겨 추가 테스트 메서드로 붙인다.
  • "앞선 태스크가 이미 통과시킨다" → 이것도 사이클이 아니다. 그 태스크에 합친다.

이 줄들은 필터이지 산출물이 아니다 — task.md나 다른 어디에도 쓰지 않는다. 살아남은 태스크만 제시한다.

제시하기 전에 이것을 돌린다. 돈이 쓰이기 전에 작동하는 유일한 통제 수단이기 때문이다. ALREADY_PASSES 백스톱은 Red일 수 없었던 작업에 RED 디스패치, 리뷰어, 테스트 실행을 이미 태운 뒤에야 울린다. 측정된 한 세션에서는 그런 사이클 두 개가 전체 에이전트 시간의 41%를 차지했다.

태스크 목록을 이 형식으로 제시하고, 시작하기 전에 사용자 확인을 받는다.

5.세션 컨텍스트 파일 작성

첫 사이클 전에 오케스트레이터가 기능 영역을 한 번 탐색하고 {TDD_DIR}/context.md를 쓴다. 이번 세션에서 직접 확인한 것만 쓴다. 서술하려는 스키마를 덤프하고, 인용하려는 시그니처의 클래스를 열어 보고, 주입하라고 지시하기 전에 그 빈이 존재하는지 확인한다. 확인하지 않고 기억으로 적은 사실은 이 파일에서 가장 비싼 줄이다. 틀리거나 부분적인 사실은 나중에 에이전트가 발견하는데, 그 에이전트는 이를 싸게 고칠 수 없기 때문이다. 모든 단계 에이전트는 코드베이스를 다시 스캔하는 대신, 그리고 매 디스패치마다 같은 블록을 인라인으로 받는 대신 이 파일을 읽는다.

파일은 다음 순서로 네 개의 섹션을 가진다.

## Workspace Rules
이 파일이 작성된 뒤 다른 사람이 이 워크스페이스를 수정했을 수 있다. 당신이 만들지 않은 변경은 절대 되돌리지 않는다 — 다른 사람의 진행 중인 작업이다.
커밋하지 않는다. 커밋 이력은 오케스트레이터와 사용자의 소유다.
불변성 ID(`INV-001`, …)는 세션 관리용이며 `.tdd-team/` 파일 안에만 존재한다. 프로덕션 코드나 테스트 코드에 절대 쓰지 않는다 — 주석에도, 이름에도, 메시지에도. 가드 절은 자신의 규칙을 도메인 언어로 말한다. 계획 문서의 코드 조각이 ID를 주석으로 보여주더라도 마찬가지다 — 규칙은 가져오고 태그는 버린다.

간결하게 유지한다(파일 전문이 아니라 시그니처와 경로). 기능이 완전히 새로워 인접 코드가 없다면 "관련 기존 코드 없음"이라고 적고 대상 패키지만 나열한다.

마지막 세 줄은 배경이 아니라 경계다. 모든 단계 에이전트는 각자의 컨텍스트에서 돌며 자신이 읽은 코드로부터 관례를 추론한다. 알려진 결함이 그대로 재생산되고, 아무도 건드릴 생각이 없던 파일에 수정이 내려앉는 경로가 정확히 이것이다. 출처는 계획 문서의 「구현 대상 파일」, 「목표가 아닌 것」, 「기존 코드의 함정」이다. 계획서에 함정 섹션이 없다면, 첫 사이클 전에 이 기능이 본뜨는 참조 구현을 한 번 훑는 데 시간을 쓴다. 3번 사이클에서 발견된 결함은 이미 두 번 복사된 뒤다.

함정 항목에 → 대신 무엇을 할지가 빠져 있다면 아예 적지 않느니만 못하다 — 에이전트는 무언가를 피해야 한다는 것만 알고 대체안을 스스로 지어낸다. 어떤 섹션에 적을 내용이 없다면 줄을 지우지 말고 해당 없음이라고 쓴다. 나중에 읽는 사람이 검토는 되었음을 알 수 있도록.

이 섹션들을 에이전트 프롬프트에 인라인으로 넣지 않는다. 경로를 전달한다. 사용자가 사이클 사이에 context.md를 수정할 수 있고, 인라인 사본은 그 수정을 조용히 무시하기 때문이다.

첫 사이클 전에 {TDD_DIR}/session.md를 쓴다 — 태스크 개수와 무관하게 언제나. 이어서 하기가 이 파일에 의존하며, 세션의 크기에 따라 좌우되어서는 안 된다.

feedback_mode는 문자 그대로 unset으로 적히고, 사용자가 주기 질문에 답해 per-cycle 또는 auto로 바뀔 때까지 그대로 둔다. fix_rounds_total은 세션 전체의 수정 라운드 횟수로 절대 초기화하지 않는다 — 세션 종료가 보고하는 값이다.

모든 단계 후에 해당 행을 갱신한다 — 한 줄 수정, 그 이상은 하지 않는다. 사용자가 주기 질문에 답하면 feedback_mode를, 값이 바뀔 때마다 세 카운터를 갱신한다. 갱신하지 않은 카운터는 이어서 하기를 새로 시작하는 것보다 나쁘게 만드는 유일한 실패 모드다.

TDD_STATUS 봉투

모든 단계는 정확히 이것만 반환한다. 오케스트레이터의 컨텍스트에 들어오는 유일한 것이다.

TDD_STATUS
phase: RED | GREEN | REFACTOR | CYCLE_REVIEW | FIX | FINAL_REVIEW
status: OK | BLOCKED | ALREADY_PASSES
result_file: {에이전트가 쓴 경로}
tests: {passed}/{failed}
verdict: APPROVED | NEEDS_FIX
findings: {Critical}/{Important}/{Minor}
blocked_reason: MISSING_FACT | OVERWHELMED | n/a
note: {한 줄 — status가 BLOCKED일 때만. MISSING_FACT라면 필요한 사실 하나만 지목한다.}

해당 단계에 적용되지 않는 필드는 생략하지 않고 n/a로 채운다 — 빈 값과 없는 필드는 구분 가능해야 한다.

status: ALREADY_PASSES는 RED 전용이며, 보고된 모든 메서드가 이미 통과한다는 뜻이다. 한 메서드라도 진짜로 Red라면 RED는 OK를 반환한다.

결과 파일은 봉투가 담지 못하는 세부가 필요할 때만 읽는다 — BLOCKED 진단이나 게이트 실패의 경우다. 정상적인 사이클은 결과 파일을 열지 않는다.

결과 블록 게이트

검증은 두 곳에서 일어난다. 봉투와 결과 파일은 서로 독립적으로 실패할 수 있기 때문이다.

1. 봉투 검사 — 반환값이므로 직접 읽는다. 모든 필드가 존재하고, result_file이 비어 있지 않으며, status가 세 리터럴 중 하나여야 한다.

2. 결과 파일 검사 — 파일을 컨텍스트로 읽어 들이지 않고 필수 키를 확인한다.

f={TASK_DIR}/{RESULT_FILE}
miss=$(for k in {REQUIRED_KEYS}; do grep -q "^$k:" "$f" 2>/dev/null || echo "$k"; done | tr '\n' ',')
[ -z "$miss" ] && echo PASS || echo "MISSING:$miss"
PHASEREQUIRED_KEYS
REDtest_file test_method failure stubs
GREENfiles_modified tests_passed tests_failed failure_detail
REFACTORstatus reason tests_passed deferred
FIXfindings_addressed files_modified tests_passed tests_failed notes

둘 중 하나라도 실패하면 값을 추론하지 말고 다음 단계로 넘어가지도 않는다 — 같은 에이전트를 같은 프롬프트에 무엇이 빠졌는지 지목한 한 줄만 덧붙여 다시 디스패치한다. 추측한 RED_RESULT는 GREEN을 엉뚱한 메서드로 보내고, 사이클 하나를 통째로 날린다. 이 재디스패치는 BLOCKED 예산에 계산한다. 재시도 1회, 그다음은 사용자에게 묻는다.

Agent 툴을 쓸 수 없다면 not available이라고 말하고 같은 단계를 로컬에서 실행한다.

  1. 해당 단계의 참조 파일을 읽는다.
  2. {TDD_DIR}/context.md와 {TASK_DIR}/task.md를 읽는다.
  3. 그 단계의 워크플로를 로컬에서 따르며 파일 수정에는 Edit/Write를 쓴다.
  4. 에이전트가 그러하듯 결과 블록을 {TASK_DIR}/{RESULT_FILE}에 쓴다.

사이클 흐름

  1. RED → 테스트 파일 경로, 메서드 이름, 실패 메시지를 확보한다 — 묶인 태스크는 시나리오마다 한 줄씩 보고한다
    • 보고된 모든 메서드가 ALREADY_PASSES → GREEN + REFACTOR를 건너뛰고 다음 태스크로 간다 (그래도 CYCLE REVIEWER는 돌린다 — 새 테스트가 공허하지 않은 진짜 커버리지인지 확인하는 유일한 검사다)
    • 한 메서드라도 진짜 Red → 평소대로 GREEN으로 진행한다. GREEN은 Red인 것을 겨냥하고, ALREADY_PASSES인 것들은 이미 통과하는 커버리지로 함께 따라간다
    • 빌드 실패 → RED가 내부적으로 처리한다(스텁 수정 후 재확인)
  2. GREEN → 수정된 파일과 전체 테스트 결과를 확보한다
  3. REFACTOR — GREEN 결과물이 이미 깔끔하면 건너뛴다
  4. CYCLE REVIEWER → 독립 서브에이전트를 디스패치한다 (아래 참고)

각 단계가 반환될 때마다, 다음 단계를 디스패치하기 전에 {TDD_DIR}/session.md의 해당 태스크 행(status, last_phase)을 갱신한다. 단계 사이에 죽더라도 파일은 세션이 어디서 멈췄는지 진실을 말하고 있어야 한다.

사이클 리뷰어 디스패치

먼저 사이클 diff를 만든다. 곧바로 파일로 리다이렉트한다 — diff는 절대 당신의 컨텍스트를 거쳐서는 안 된다.

paths=$(grep -hE '^(test_file|stubs|files_modified):' {TASK_DIR}/*-result.md \
  | sed 's/^[a-z_]*: *//' | tr ',' '\n' | sed 's/^ *//; s/ *$//' \
  | grep -v -e '^none$' -e '^$' | sort -u)
git diff -- $paths > {TASK_DIR}/diff.md
for f in $paths; do
  git ls-files --error-unmatch "$f" >/dev/null 2>&1 || git diff --no-index /dev/null "$f" >> {TASK_DIR}/diff.md
done
wc -l < {TASK_DIR}/diff.md

for 루프는 이번 사이클에 새로 생긴 파일들을 덧붙인다. RED의 테스트 클래스와 스텁은 추적되지 않는 파일이라 평범한 git diff는 아무것도 보고하지 않고, 이 루프가 없으면 리뷰어는 테스트가 빠진 diff를 받게 된다. git diff --no-index는 차이를 찾을 때마다 0이 아닌 코드로 종료하는데, 여기서는 그것이 정상적인 결과이지 반응해야 할 명령 실패가 아니다.

당신에게 돌아오는 것은 줄 수뿐이다. diff가 비어 있지 않은지 확인하는 데 쓴다. 0이라는 것은 아무것도 바뀌지 않았다는 뜻이며, ALREADY_PASSES 사이클이 아닌 이상 이는 리뷰할 수 있는 상태가 아니라 멈춰 설 만한 결함이므로, 리뷰어를 디스패치하지 말고 멈춰서 묻는다.

알려진 한계: 에이전트는 커밋하지 않으므로, 앞선 사이클이 이미 건드린 파일은 그 사이클의 변경까지 여기에 함께 보인다. 리뷰어에게는 red-result.md에 지목된 메서드에 집중하라고 지시하므로 잡음은 제한된다. 사이클마다 커밋하면 없앨 수 있지만 그것은 "에이전트는 커밋하지 않는다" 규칙을 바꾸는 일이라 범위 밖이다.

REFACTOR가 끝나면 독립 리뷰어 서브에이전트를 디스패치하되, GREEN(또는 수정 에이전트)이 보고한 테스트 결과를 함께 넘겨 방금 돌린 것을 다시 돌릴 이유가 없게 한다. Agent 툴을 쓸 수 없다면 not available이라고 말하고 references/cycle-reviewer.md를 사이클 diff에 로컬로 적용한다.

Agent({
  subagent_type: "general-purpose",
  description: "CYCLE REVIEW: {task description}",
  prompt: """
{SKILL_DIR}/references/cycle-reviewer.md를 읽는다 — 이 파일에 접근할 권한이 있다.
정확히 그대로 따른다.

시작하기 전에 다음을 읽는다:
- {TDD_DIR}/context.md — 환경, 도메인 불변성, 워크스페이스 규칙
- {TASK_DIR}/task.md — 리뷰 대상 태스크
- {TASK_DIR}/diff.md — 당신이 판정할 사이클 diff
- {TASK_DIR}/red-result.md — 이 사이클이 추가한 테스트 메서드. 리뷰는 여기에 집중한다
- {TASK_DIR}/green-result.md — 이미 완료된 테스트 실행 결과. 다시 실행하지 않는다
- 수정 라운드 이후 재리뷰라면 green-result.md 대신 {TASK_DIR}/fix-result.md를 읽는다 — 현재 테스트 실행 결과가 거기 있다. 다시 실행하지 않는다
- RED가 모든 메서드에 대해 `ALREADY_PASSES`를 보고했다면 green-result.md는 없다 — 모든 메서드가 통과함을 이미 기록한 red-result.md에 의존한다

전체 리뷰 보고서를 {TASK_DIR}/review.md에 쓴다.
TDD_STATUS 봉투만 반환한다.
"""
})

리뷰어 판정 처리 (review.md가 아니라 봉투의 verdict와 findings에서 읽는다):

  • APPROVED → session.md를 갱신하고, fix_rounds_this_cycle을 0으로, consecutive_needs_fix를 0으로 되돌린 뒤 다음 태스크로 간다
  • NEEDS_FIX이고 Critical 또는 Important > 0 → 수정 에이전트를 디스패치하고(수정 에이전트 디스패치 참고) 사이클 리뷰어를 다시 돌린다. 매 라운드 전에 session.md의 fix_rounds_this_cycle과 fix_rounds_total을 모두 증가시킨다.
  • NEEDS_FIX인데 Minor만 있음 → 기록하고 계속 진행한다. Minor는 절대 수정 라운드를 유발하지 않는다

수정 라운드 예산

사이클당 최대 2라운드. 한 라운드는 수정 에이전트 디스패치 1회와 리뷰어 재실행 1회다.

횟수는 머릿속이 아니라 {TDD_DIR}/session.md의 fix_rounds_this_cycle에 산다 — 이어서 하는 세션은 이미 쓴 라운드를 알아야 한다.

새 태스크를 시작할 때는 이전 태스크가 무엇으로 끝났든 0으로 되돌린다 — APPROVED 판정이든, 사용자가 그대로 두기로 한 소진된 예산이든, Minor만 담긴 NEEDS_FIX든 마찬가지다. 스스로 초기화되는 것은 APPROVED 경로뿐이므로, 이 규칙이 없으면 다음 사이클이 쓰지도 않은 라운드를 물려받는다.

두 번째 라운드 후에도 리뷰어가 NEEDS_FIX를 반환하면, 세 번째를 디스패치하지 말고 루프를 멈춰 결정을 사용자에게 넘긴다.

"{태스크}에서 리뷰어가 2회 수정 후에도 지적을 남겼습니다: {미해결 findings}. 이대로 두고 다음 태스크로 갈까요, 직접 손보실까요, 아니면 이 태스크를 다시 설계할까요?"

두 번으로 풀리지 않은 것이 세 번째 라운드로 풀리는 일은 거의 없다. 대개 그 지적이 코드가 아니라 태스크의 설계에 관한 것이라는 뜻이고, 그것은 사용자가 판단할 몫이다.

서킷 브레이커

3개 사이클 연속으로 NEEDS_FIX가 돌아오면 새 사이클을 시작하지 않는다. 반복되는 원인은 거의 항상 상류에 있다 — 의도한 바를 말하지 못하는 불변성이거나, 코드가 구성되기를 원하는 방식과 맞지 않는 태스크 분해다. 패턴을 보고하고 사용자와 함께 Setup 3~4단계로 돌아간다.

"최근 3개 사이클이 연속으로 수정 요청을 받았습니다: {사이클별 findings 한 줄 요약}. 개별 코드 문제라기보다 불변성 정의나 태스크 분해 쪽 문제로 보입니다. Setup의 불변성 표와 태스크 목록을 다시 확인할까요?"

횟수는 {TDD_DIR}/session.md의 consecutive_needs_fix에 산다. 이것은 판정이 아니라 사이클을 센다. 사이클이 APPROVED 없이 끝나면 정확히 1만큼 증가시키고, APPROVED로 끝나면 0으로 되돌린다. 한 사이클은 첫 리뷰와 두 번의 수정 라운드를 합쳐 NEEDS_FIX 판정 세 개를 낼 수 있지만 그래도 하나로 센다. 판정을 세면 한 사이클 안에서 브레이커가 떨어지는데, 그것은 브레이커의 메시지가 주장하는 상황이 아니다.

피드백 주기

피드백의 단위는 사이클이다. 사이클은 리뷰어가 APPROVED를 반환할 때 — 필요했던 수정 라운드를 모두 거친 뒤 — 완료된다. 멈춰 설 가치가 있는 지점은 그 한 곳이다. 테스트, 구현, 리팩터링, 그리고 그 셋에 대한 독립 리뷰가 한 상에 함께 올라와 있고, 사용자가 바꾸고 싶은 무엇이든 아직 사이클 하나 분량의 작업이기 때문이다. 사이클 안에서 단계 사이에 멈추지 않는다.

프로젝트 지시(CLAUDE.md)가 각 단계마다 피드백을 요구한다면, 단계 사이에 네 번 멈추는 대신 여기, 사이클 단위로 지킨다. RED 뒤의 멈춤은 리뷰가 붙지 않은 절반짜리 사이클을 사용자에게 건네는 것이고, 그것은 그 지시가 요구하는 점검이 아니다. 그 중간 멈춤이 대신하려던 역할이 바로 사이클 리뷰어다. 단계별 지시가 실제로 바꾸는 것은 아래의 기본값이다. per-cycle이 필수가 되므로 auto를 제안하지 않고 기록하지도 않는다.

1번 사이클은 무조건 멈춘다. 다른 무엇과도 무관하다 — 불변성, 테스트 관례, 태스크 단위가 옳았는지를 드러내는 사이클이기 때문이다. 그 게이트 직후에 정확히 한 번만 묻는다.

"1번 사이클이 끝났습니다. 남은 {N}개 사이클은 이어서 자동으로 진행할까요, 아니면 사이클마다 확인받을까요?
(.tdd-team/context.md나 각 태스크의 task.md를 직접 수정하시면 다음 단계부터 반영됩니다.)"

답을 {TDD_DIR}/session.md에 feedback_mode로 기록하고 남은 세션 동안 따른다. auto를 덮는 예외는 두 가지다.

  • 수정 라운드 예산이 소진된 경우
  • 서킷 브레이커가 작동한 경우

둘 다 어떤 모드가 켜져 있든 멈추고 묻는다.

수정 에이전트 디스패치

사이클 리뷰어와 최종 리뷰어의 판정, 그리고 실패한 Final Review 테스트 실행이 모두 사용한다. 에이전트에게는 findings 목록 자체를 건넨다 — 리뷰 보고서 전문도 아니고, 그것이 유래한 문서도 아니다. Agent 툴을 쓸 수 없다면 not available이라고 말하고 references/fix-agent.md를 같은 findings에 로컬로 적용한다.

Agent({
  subagent_type: "general-purpose",
  description: "FIX: {short summary of findings}",

{SKILL_DIR}/references/fix-agent.md를 읽는다 — 이 파일에 접근할 권한이 있다.

Final Review 중에는 TASK_DIR이 정의되어 있지 않으므로 최종 리뷰의 수정을 절대 태스크 디렉터리로 향하게 하지 않는다. {TASK_DIR}/fix-result.md는 사이클 리뷰어의 입력이자 diff 경로의 출처이고, 어떤 태스크의 사본을 덮어쓰면 둘 다 망가진다. 수정 에이전트는 findings를 직접 읽는다 — 당신이 중계하지 않는다.

재실행 때 리뷰어에게 건네는 것은 봉투의 tests 필드다. 그래야 리뷰어가 테스트를 다시 돌릴 이유가 없다.

BLOCKED 처리

막힌 에이전트는 서로 다른 두 가지 문제 중 하나를 보고하고 있으며, 둘은 정반대의 대응을 필요로 한다. 무엇을 하기 전에 blocked_reason부터 읽는다.

MISSING_FACT — context.md에 없는 것을 에이전트가 필요로 한다.

직접 해결해서 넘겨준다. 당신에게는 워크스페이스 전체가 있고 툴 호출은 몇 초면 끝나지만, 에이전트에게는 패키지 하나뿐이라 같은 답에 도달하려면 추론으로 파고들어야 한다. 실제 세션에서 측정한 결과, 이 오케스트레이터가 몇 초 만에 덤프할 수 있는 스키마 하나를 서브에이전트가 재구성하는 데 30분이 걸렸고, 그렇게 재구성한 결과마저 틀렸다.

  1. 사실을 확보한다 — 데이터베이스를 조회하고, 파일을 열고, 그 빈이 실제로 존재하는지 확인한다.
  2. {TDD_DIR}/context.md의 해당 섹션에 덧붙인다. 이후의 모든 디스패치가 이를 물려받으므로 같은 공백에 두 번 비용을 치르지 않는다.
  3. 동일하고 잘라내지 않은 컨텍스트로 같은 호출을 다시 디스패치한다. 무엇도 크지 않았다. 무언가가 없었을 뿐이다.

절대 MISSING_FACT에 컨텍스트를 잘라내는 것으로 답하지 않는다 — 방금 부족하다고 말한 것을 더 없애는 일이기 때문이고, 잘라낸 재시도를 예상하는 에이전트가 보고 대신 탐색을 배우게 되는 이유이기도 하다. 이 라운드는 어떤 예산에도 계산되지 않는다. 재시도가 아니라 설계대로 동작하는 저비용 경로다. 사실을 직접 해결할 수 없다면 사용자에게 묻는다 — 재디스패치하지도, 에이전트가 찾으러 가게 두지도 않는다.

OVERWHELMED — 에이전트가 필요한 것을 모두 가졌는데도 진행하지 못한다.

컨텍스트를 줄여 한 번만 재디스패치한다. Project Context 섹션을 잘라낸 사본 — 대상 패키지와 에이전트가 필요로 하는 시그니처 한두 개만 — 을 {TRIMMED_CONTEXT_FILE}에 쓰고, 재시도 프롬프트가 전체 context.md 대신 그 파일을 가리키게 한다.

{TRIMMED_CONTEXT_FILE}은 어떤 디스패치를 재시도하는지에 따라 달라진다.

재시도 대상{TRIMMED_CONTEXT_FILE}
사이클 디스패치 (RED, GREEN, REFACTOR, 사이클 리뷰어, 사이클 수정 에이전트){TASK_DIR}/context-trimmed.md
최종 리뷰어 또는 최종 리뷰 수정 에이전트{TDD_DIR}/context-trimmed.md

Final Review 중에는 TASK_DIR이 정의되어 있지 않으므로, 컨텍스트를 줄인 재시도를 절대 태스크 디렉터리로 향하게 하지 않는다.

그 재시도 이후에도 BLOCKED라면 → 디스패치를 멈추고 사용자에게 묻는다.

"{역할} 에이전트가 '{사유}'로 막혔습니다. 이 태스크를 로컬에서 직접 진행할까요, 아니면 건너뛰고 다음 태스크로 갈까요?"

같은 호출에 세 번째 디스패치를 쓰지 않는다.

Final Review

Final Review

모든 사이클이 끝나면 이번 세션에서 건드린 테스트 클래스만 실행한다 — 모든 RED_RESULT의 서로 다른 test_file 값들을 하나의 TEST_SCOPED_CMD 호출에 함께 넣는다(Gradle: ./gradlew test --tests "FQCN1" --tests "FQCN2" … --offline). 전체 TEST_CMD로 넘어가는 것은 사용자가 요청하거나, 변경이 간접 호출자가 많은 대상(공용 유틸리티, 널리 쓰이는 기반 클래스)을 건드렸을 때뿐이다.

실패하는 것이 있으면 먼저 수정 에이전트를 디스패치한다. 이 경로에는 리뷰 findings가 없고 실패한 실행 결과만 있으므로, 당신이 주지 않으면 수정 에이전트에게는 입력이 없다. 실패한 실행의 출력을 {TDD_DIR}/test-failure.md로 리다이렉트하고 그 경로를 {REVIEW_FILE}로 전달한다. diff를 만들 때와 마찬가지로 컨텍스트로 읽어 들이지 말고 파일로 리다이렉트한다. 수정 라운드 후에는 범위를 좁힌 테스트를 다시 실행한다.

이 루프도 이 스킬의 다른 모든 재시도처럼 제한된다. 최대 2라운드. 두 번째 수정 라운드 후에도 범위를 좁힌 테스트가 여전히 실패하면, 세 번째를 디스패치하지 말고 멈춰서 사용자에게 묻는다.

"Final Review 테스트가 2회 수정 후에도 실패합니다: {실패 내용}. 이대로 두고 다음 단계로 갈까요, 직접 손보실까요?"

테스트가 통과했거나 사용자가 그대로 진행하기로 선택한 뒤에만 최종 리뷰어로 넘어간다.

그런 다음 독립 최종 리뷰어를 디스패치하되, 범위를 좁힌 실행의 결과를 함께 넘겨 다시 실행할 이유가 없게 한다. Agent 툴을 쓸 수 없다면 not available이라고 말하고 references/final-reviewer.md를 태스크 목록, 불변성, 브랜치 diff에 로컬로 적용한다.

먼저 사이클 diff와 같은 방식으로 브랜치 diff를 파일로 만든다.

git diff > {TDD_DIR}/branch-diff.md
git ls-files --others --exclude-standard -- {SOURCE_DIR} {TEST_DIR} | while read -r f; do
  git diff --no-index /dev/null "$f" >> {TDD_DIR}/branch-diff.md
done
wc -l < {TDD_DIR}/branch-diff.md

두 번째 명령은 이번 세션에 생성된 모든 파일을 덧붙인다. 새 테스트 클래스와 새 프로덕션 클래스는 추적되지 않으며 git diff만으로는 누락되어, 최종 리뷰어가 각 태스크에 테스트가 없다고 결론짓게 된다. --exclude-standard가 이미 .git/info/exclude를 존중하므로 {TDD_DIR} 자체는 건너뛴다. {SOURCE_DIR}과 {TEST_DIR}로 범위를 좁히면 사용자 저장소의 무관한 미추적 파일이 들어오지 않는다. git diff --no-index는 차이를 찾으면 0이 아닌 코드로 종료하는데, 여기서는 그것이 기대되는 결과다.

최종 리뷰어 판정 처리:

  • APPROVED → 세션 종료로 넘어간다
  • NEEDS_FIX → 완전한 findings 목록과 함께 수정 에이전트를 한 번 디스패치하고(수정 에이전트 디스패치 참고) 최종 리뷰어를 다시 돌린다. 매 라운드 전에 session.md의 fix_rounds_total을 증가시킨다. Agent 툴을 쓸 수 없다면 로컬에서 고친다.

수정 라운드 예산은 여기에도 적용된다. 최대 2라운드. 두 번째 이후에도 findings가 남으면, 세 번째 라운드를 디스패치하지 말고 미해결로 나열한 채 세션을 종료하며 요약에 그 사실을 분명히 적는다.

.tdd-team/은 그대로 둔다. 세션의 디버깅 기록이자 이후 이어서 하기의 입력이며, git 추적에서 제외되어 있으므로 유지해도 사용자에게 비용이 들지 않는다.

판정이 APPROVED WITH UNRESOLVED FINDINGS라면 그 아래에 미해결 항목을 나열한다. 소진된 예산으로 끝난 세션에 APPROVED를 출력하지 않는다.
