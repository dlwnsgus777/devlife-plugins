# tdd-team

에이전트 기반 Red-Green-Refactor TDD 사이클을 자동으로 실행합니다.  
`red`, `green`, `refactor` 세 에이전트가 순차적으로 실행되며 한 번에 하나의 동작 단위를 구현합니다.

## 언제 사용하나요?

- TDD 사이클을 에이전트에게 위임하고 싶을 때
- 요구사항 문서(스펙·계획서·티켓·PRD 등)가 있고, 테스트 우선으로 기능을 구현할 때
- 단계별로 구현하면서 각 사이클에서 피드백을 받고 싶을 때

> 구현 후 테스트를 작성하거나, 기존 테스트를 실행하거나, 테스트 실패를 디버깅하는 용도로는 사용하지 않습니다.

## 트리거 문구

```
"TDD로 개발해줘"
"TDD로 구현해줘"
"TDD 시작"
"TDD 팀 만들어"
"테스트 주도 개발"
"테스트 먼저 작성하고 싶어"
"테스트부터 짜줘"
"이 기능 테스트 먼저 만들고 하나씩 구현하자"
```

## 실행 흐름

### 준비 단계

0. **재개 여부 확인** — `.tdd-team/session.md`가 있으면 진행 상황({완료}/{전체} 태스크, 마지막 단계)을 보여주고 이어서 진행할지 새로 시작할지 확인합니다. 이어서 진행하면 `context.md`·`session.md`를 그대로 채택하고 준비 단계 나머지를 건너뛰며, `feedback_mode`·연속 `NEEDS_FIX` 횟수·사이클 내 수정 횟수·세션 전체 누적 수정 횟수까지 복원합니다(0부터 다시 세면 이전 세션이 이미 쓴 수정 라운드를 또 쓰게 됨). 새로 시작하면 기존 `.tdd-team/`을 삭제하지 않고 `.tdd-team/archive-{YYYYMMDD-HHMMSS}/`로 옮겨 보존한 뒤 처음부터 진행합니다. 재개 여부 확인은 `.tdd-team/session.md` 이 정확한 경로만 보므로, `archive-*/` 안으로 옮겨진 `session.md`는 다음 실행에서 재개 대상으로 잡히지 않습니다.
1. **도메인 불변성 도출** — PRD 또는 요구사항에서 비즈니스 규칙 추출

```
도메인 불변성 (비즈니스 규칙)

  ┌─────┬─────────────────────────────────────────────────────┐
  │  #  │                       불변성                        │
  ├─────┼─────────────────────────────────────────────────────┤
  │ 1   │ 결제 완료 상태의 주문 금액은 변경할 수 없다            │
  ├─────┼─────────────────────────────────────────────────────┤
  │ 2   │ 취소된 주문은 재활성화할 수 없다                      │
  └─────┴─────────────────────────────────────────────────────┘
```

2. **태스크 분해** — 각 불변성을 `@DisplayName`이 될 도메인 규칙 문장으로 표현 후 사용자 확인. 문서가 이미 순서 있는 태스크 목록을 담고 있으면 새로 도출하지 않고 그대로 채택하되, 아래 커버리지 하한과 병합 규칙은 동일하게 적용
   - **커버리지 하한 (상한이 아님)** — 불변성 하나는 테스트 하나가 아니라 **경계**를 짚어야 합니다. 규칙을 어기는 케이스 + 바로 옆의 지키는 케이스 + 규칙이 직접 언급하는 다른 상태/입력("결제 완료 상태에서는"이라면 결제 대기·부분 환불도 규칙이 그은 경계입니다). 여기에 클래스당 해피패스 1개를 더한 것이 하한이며, 도메인 근거가 있으면 얼마든지 넘어갑니다
   - **TDD에서는 커버리지 문제가 아닙니다** — GREEN은 테스트가 요구하는 것만 구현하므로, 테스트 없는 엣지 케이스는 "검증 안 된 동작"이 아니라 **"구현되지 않은 동작"**입니다. 빼도 되는 건 언어·프레임워크·단순 접근자를 검사하는 시나리오뿐이고, 도메인 규칙의 경계는 절대 아닙니다
   - **이건 사이클을 늘리지 않습니다** — 한 규칙의 경계 케이스들은 같은 가드 절을 공유하므로 한 태스크에 묶이고, RED가 같은 규칙·다른 입력을 `@ParameterizedTest` 하나로 씁니다. 비싼 건 테스트 메서드 수가 아니라 사이클 수입니다
   - 계획 문서의 `[REGRESSION]` 항목은 사이클이 아닙니다 — "기존 커버리지로 확인"으로 한 번만 적고 Final Review에서 함께 실행하며, `[NEW]`만 사이클이 됩니다
   - **하나의 구현 변경으로 통과하는 시나리오는 한 태스크로 묶습니다** — 한 사이클은 테스트 메서드 1개가 아니라 *구현 작업 단위*에 대응합니다. 같은 가드절·같은 분기·같은 작은 함수로 해결되는 시나리오 그룹(예: 한 검증의 성공/실패 분기)은 `@DisplayName` 여러 개를 가진 단일 태스크로 병합
   - 너무 굵게 묶은 신호: GREEN이 한 번의 작은 변경으로 모든 테스트를 통과시킬 수 없음 → 다시 분리
   - **목록을 보여주기 전에, 태스크마다 「이 테스트를 실패→통과로 만드는 생산 코드 변경」을 한 줄로 답해봅니다** — 구체적인 변경(가드 절·새 메서드·분기)이 있으면 사이클이고, "없음(이미 동작함)"이나 "앞선 태스크가 이미 통과시킴"이면 사이클이 아니라 커버리지입니다. 해당 로직을 만드는 태스크에 테스트 메서드로 병합합니다. 이 답변은 필터일 뿐이라 `task.md` 등 어디에도 기록하지 않습니다
   - 이 체크가 **비용을 쓰기 전에 작동하는 유일한 통제**입니다. 아래 `ALREADY_PASSES` 신호는 RED 디스패치·리뷰어·테스트 실행을 이미 태운 *뒤*에 뜹니다 — 실측 세션에서 Red가 될 수 없는 사이클 2개가 전체 에이전트 시간의 41%를 썼습니다
   - 너무 잘게 쪼갠 신호(백스톱): 사이클 N의 RED가 `ALREADY_PASSES`로 돌아옴 (N-1의 구현이 이미 커버) → 이후 태스크를 병합. 위 체크가 걸렀어야 할 것이므로, 이 신호가 뜨면 남은 태스크 전체에 체크를 다시 돌립니다
3. **프로젝트 컨텍스트 캡처 (1회)** — 오케스트레이터가 기능 영역을 한 번만 탐색해 `.tdd-team/context.md`에 프로젝트 컨텍스트(패키지 구조, 테스트/픽스처 컨벤션, 관련 타입 시그니처, 도메인 앵커, **구현 대상 파일 · 목표가 아닌 것 · 기존 코드의 함정**)를 기록. 이후 RED/GREEN/REFACTOR 에이전트는 코드를 재탐색하지 않고 이 파일을 경로로 전달받아 참조
   - **뒤의 세 항목은 배경이 아니라 경계입니다** — 각 phase 에이전트는 자기 컨텍스트에서 실행되며 자기가 읽은 코드로부터 컨벤션을 추론합니다. 알려진 결함이 그대로 복제되고 아무도 건드릴 생각이 없던 파일에 수정이 들어가는 경로가 정확히 여기입니다
   - 출처는 계획 문서의 「구현 대상 파일」·「목표가 아닌 것」·「기존 코드의 함정」입니다. 계획에 함정 섹션이 없으면 첫 사이클 전에 이 기능이 모방할 참조 구현을 한 번 훑습니다 — 3번 사이클에서 발견한 결함은 이미 두 번 복제된 뒤입니다
   - **함정 항목에는 `→ 무엇을 대신할지`가 반드시 붙습니다** — 대안 없이 "피하라"만 주면 에이전트가 자기 나름의 대체안을 발명해서 같은 버그의 세 번째 변종이 나옵니다. 해당 내용이 없으면 줄을 빼지 말고 `해당 없음`으로 적어 검토했다는 사실을 남깁니다
4. **세션 파일 기록** — 태스크 수와 무관하게 항상 `.tdd-team/session.md`에 태스크·상태·마지막 단계와 함께 `feedback_mode`·재시도 카운터(`consecutive_needs_fix`, `fix_rounds_this_cycle`, `fix_rounds_total`)를 기록하고 사이클마다 한 줄씩 갱신합니다. 세션이 중단되거나 컨텍스트가 압축돼도 준비 단계 0에서 이어갈 수 있습니다. (구 경로 `docs/tdd/session-{feature}.md`는 폐기되었습니다.)

> 계획 문서가 불변성에 `INV-001` 같은 ID를 부여했다면 그대로 이어받아 세션 내내 사용합니다 — Final Review의 커버리지 대조가 판단이 아닌 조회가 됩니다.
> 다만 ID는 `.tdd-team/` 산출물 안에서만 씁니다 — 계획 문서 스니핏이 `// INV-001` 주석을 달고 있더라도 생산·테스트 코드의 주석·이름·메시지에는 넣지 않고, 규칙만 도메인 언어로 옮깁니다.

### 산출물 구조 (`.tdd-team/`)

프로젝트 루트에 `.tdd-team/` 디렉토리를 만들어 세션의 모든 산출물을 파일로 남깁니다.

- `context.md` — 환경 정보·프로젝트 컨텍스트·도메인 불변성·워크스페이스 규칙 (준비 단계에서 1회 작성)
- `session.md` — 태스크 목록·진행 상태·`feedback_mode`·재시도 카운터
- `task-NN/` — 태스크별 `task.md`, `red-result.md`, `green-result.md`, `refactor-result.md`, `diff.md`, `review.md`, `fix-result.md`
- `branch-diff.md`, `final-review.md` — Final Review 산출물

각 에이전트는 프롬프트로 경로만 전달받아 필요한 파일을 직접 읽고, 작업 결과 전문은 위 파일에 쓴 뒤 `TDD_STATUS` 봉투(`phase`/`status`/`result_file`/`tests`/`verdict`/`findings`/`note`) 한 장만 반환합니다 — 결과 전문이 오케스트레이터의 컨텍스트에 쌓이지 않습니다.

사이클 사이에 `context.md`나 각 태스크의 `task.md`를 사용자가 직접 수정하면 다음 디스패치부터 반영됩니다. `.tdd-team/`은 `.git/info/exclude`로 추적 제외되어(사용자의 `.gitignore`는 건드리지 않음) 세션이 끝나도 디버깅 기록으로 남습니다.

### TDD 사이클 실행 (태스크당)

```
RED 에이전트
└── 실패하는 테스트 작성 → 컴파일만 먼저 확인 → 테스트 1회로 실패 확인
    ↓
GREEN 에이전트
└── 테스트를 통과하는 최소 코드 작성
    ↓
REFACTOR 에이전트
└── 코드 품질 개선 (테스트 통과 유지) · 커밋하지 않음
    ↓
CYCLE REVIEWER
└── 독립 서브에이전트가 사이클 diff 검토 (APPROVED / NEEDS_FIX)
    └── NEEDS_FIX → FIX 에이전트가 지적 사항만 수정 → 리뷰어 재실행 (최대 2라운드)
    ↓
⛔ 체크포인트 — 1번 사이클은 무조건 대기, 이후는 선택한 모드에 따름
    ↓
다음 태스크
```

### 재시도 예산

이 스킬의 모든 재시도에는 상한이 있고, 예산이 끝나면 한 번 더 시도하는 대신 **사용자에게 묻습니다**.

| 상황 | 예산 | 소진 후 |
|---|---|---|
| 에이전트 `BLOCKED` · `MISSING_FACT` | 예산 없음 — 오케스트레이터가 사실을 구해 `context.md`에 추가 후 재디스패치 | 사실을 못 구하면 사용자 질문 |
| 에이전트 `BLOCKED` · `OVERWHELMED` | 컨텍스트 축소 재시도 1회 | 로컬 진행 / 건너뛰기 질문 |
| 결과 블록 누락·불완전 | 재디스패치 1회 | 사용자 질문 (값을 추측하지 않음) |
| 리뷰어 `NEEDS_FIX` | 수정 2라운드 | 미해결 findings와 함께 사용자 판단 |
| GREEN 통과 실패 | 시도 2회 | `BLOCKED` 처리 |
| 3사이클 연속 `NEEDS_FIX` | — | 사이클 중단, 불변성·태스크 분해 재확인 |

마지막 항목이 서킷 브레이커입니다. 같은 지적이 반복되면 개별 코드가 아니라 불변성 정의나 태스크 분해가 원인인 경우가 대부분이라, 새 사이클을 더 돌리지 않고 준비 단계로 돌아갑니다.

### 피드백 주기

**피드백 단위는 사이클입니다.** 사이클은 리뷰어가 `APPROVED`를 반환했을 때(필요했던 수정 라운드까지 끝난 뒤) 완료됩니다. 그 시점이 멈출 가치가 있는 유일한 지점입니다 — 테스트·구현·리팩터링과 그 셋에 대한 독립 리뷰가 한자리에 올라와 있고, 바꾸고 싶은 게 있어도 아직 사이클 하나 분량입니다. **사이클 중간(RED→GREEN 등)에서는 멈추지 않습니다.**

프로젝트 지시(`CLAUDE.md`)가 단계마다 피드백을 요구하더라도 **사이클 단위로 지킵니다** — RED 직후에 멈추면 리뷰가 붙지 않은 반쪽짜리 사이클을 건네는 셈이고, 그 중간 정지가 대신하려던 역할이 바로 사이클 리뷰어이기 때문입니다. 다만 그런 지시가 있으면 `per-cycle`이 하한이 되어 자동 진행 모드는 제안하지 않습니다.

별도 규칙이 없으면 **1번 사이클만 게이트하고 한 번 묻습니다** — 불변성·테스트 컨벤션·태스크 단위가 맞았는지는 첫 사이클에서 드러나기 때문입니다.

> "1번 사이클이 끝났습니다. 남은 N개 사이클은 이어서 자동으로 진행할까요, 아니면 사이클마다 확인받을까요?
> (`.tdd-team/context.md`나 각 태스크의 `task.md`를 직접 수정하시면 다음 단계부터 반영됩니다.)"

선택한 모드는 세션 끝까지 유지되지만, **재시도 예산 소진과 서킷 브레이커는 자동 모드에서도 무조건 멈춥니다.**

### 규모에 따라 줄일 것과 줄이지 말 것

**RED/GREEN 분리는 변경 크기와 무관하게 절대 생략하지 않습니다.** 테스트와 구현을 한 주체가 함께 쓰면, 테스트가 "요구사항을 압박하는" 것이 아니라 "이미 만들려던 것을 서술하는" 방향으로 흘러 해피패스만 덮게 됩니다. RED는 항상 GREEN의 구현 방식을 모르는 상태로 실행되고 GREEN은 항상 별도 디스패치로 실행됩니다.

변경 크기·위험도에 따라 줄어드는 것은 그 격리 *주변*입니다.

| 항목 | 축소 방식 |
|---|---|
| 사이클 단위 | 같은 구현 변경을 공유하는 시나리오를 한 태스크로 배치 |
| REFACTOR | GREEN 결과가 이미 깔끔하면 스킵 |
| Cycle Reviewer 깊이 | 기본은 정적 추론. 실제 코드를 변형해 재실행하는 실험은 `ALREADY_PASSES` 사이클에만, 그때도 `--rerun-tasks`/`--rerun`/`clean` 금지 |
| Final Review 범위 | 이번 세션에 건드린 테스트 클래스만 (전체 스위트는 옵트인) |

### 사이클 요약 예시

```
── TDD Cycle 1 Complete ──
RED:      ✅ Test written: 결제_완료_주문은_취소할_수_없다
GREEN:    ✅ Implementation: OrderCancelService.cancel() 예외 처리 추가
REFACTOR: ✅ 메서드명 명확화, 중복 제거
Tests: 5 passed, 0 failed

[x] 1. 취소 불가 검증   [>] 2. 환불 금액 계산   [ ] 3. 이벤트 발행
```

## 실행 방식

- RED / GREEN / REFACTOR / Cycle Reviewer / Final Reviewer / FIX 단계 모두 서브에이전트로 위임
- **FIX 에이전트** — 리뷰어가 `NEEDS_FIX`를 반환하거나 Final Review의 테스트 실행이 실패했을 때 투입됩니다. 전달받은 지적 사항만 최소 수정하고(주변 코드 정리·기능 추가·테스트 삭제 금지) 해당 클래스만 한 번 재실행해 `FIX_RESULT`를 보고 → 이 결과를 리뷰어 재실행 시 함께 넘겨 같은 테스트를 또 돌리지 않게 합니다
- 서브에이전트 도구를 사용할 수 없는 경우 `not available`로 표시 후 로컬 실행으로 전환
- 프로젝트 CLAUDE.md에 "각 단계 후 피드백 요청" 규칙이 있으면 RED → GREEN → REFACTOR → 리뷰 단계마다 사용자 승인 대기

### 탐색 대신 에스컬레이션

에이전트가 모르는 것을 만나면 **찾지 말고 보고합니다.** 같은 사실을 얻는 비용이 위치에 따라 크게 다르기 때문입니다 — 오케스트레이터는 워크스페이스 전체에 툴을 바로 쓰지만, 서브에이전트는 자기 패키지 안에서 추론으로 도달해야 합니다. 실측 세션에서 오케스트레이터가 수 초에 덤프할 수 있는 스키마를 서브에이전트가 30분에 걸쳐 재구성했고, 그나마 틀렸습니다.

- 디스패치 프롬프트에 **스코프 펜스**가 들어갑니다 — 지정된 파일·패키지 밖은 열지 않음
- 필요한 사실이 없으면 `BLOCKED` + `blocked_reason: MISSING_FACT` + 무엇이 없는지 한 줄
- 오케스트레이터가 직접 구해 `context.md`에 **추가**하고, 컨텍스트를 **줄이지 않은 채** 같은 호출을 재디스패치 — 이후 모든 디스패치가 그 사실을 물려받으므로 같은 공백을 두 번 지불하지 않음
- Setup의 `context.md`는 **이번 세션에서 확인한 것만** 적습니다. 기억으로 적은 사실 하나가 나중에 에이전트의 탐색 시간으로 환산됩니다
- `OVERWHELMED`로 막힌 경우: 컨텍스트를 줄여 **한 번만** 더 시도한 뒤 사용자에게 묻습니다 (같은 호출에 3번째 디스패치는 없음). `MISSING_FACT`는 이 경로를 타지 않습니다 — 축소가 아니라 보강이 필요하기 때문입니다

### 프롬프트 공통 블록

에이전트 프롬프트에 반복되던 두 요소는 `context.md`에 한 번만 기록되고, 6개 디스패치(RED/GREEN/REFACTOR/Cycle Review/FIX/Final Review) 모두 그 경로를 참조합니다 — 매번 프롬프트에 인라인으로 넣지 않습니다.

- **ENVIRONMENT** — `PROJECT_ROOT`/`SOURCE_DIR`/`TEST_DIR`/`TEST_SCOPED_CMD`/`TEST_FRAMEWORK`. 리뷰어에게도 전달합니다 (Verification Depth 규정상 직접 실행이 필요한 좁은 경우가 있음)
- **워크스페이스 규칙** — 다른 에이전트나 사용자가 만든 변경을 되돌리지 말라는 경고, 커밋 금지

### 테스트 실행 최적화

사이클 시간의 대부분을 차지하던 "매 단계 전체 테스트 스위트 실행"을 제거했습니다.

- **사이클 중에는 작업 중인 테스트 클래스만 실행** (`TEST_SCOPED_CMD`, 예: `./gradlew test --tests "FQCN" --offline`)
- **Final Review는 이번 세션에 건드린 테스트 클래스만** 한 번에 모아 실행 (`--tests "FQCN1" --tests "FQCN2" ...`). GREEN/REFACTOR가 이미 각 클래스를 개별 실행했으므로 교차 클래스 회귀도 대부분 여기서 잡힙니다
- **전체 스위트(`TEST_CMD`)는 기본 실행하지 않습니다** — 사용자가 명시적으로 전체 회귀 확인을 요청하거나, 공유 유틸·광범위한 베이스 클래스처럼 간접 호출자가 많은 지점을 건드린 경우에만 실행
- **RED는 컴파일을 먼저 통과시킨 뒤에 테스트를 돌립니다** (`TEST_COMPILE_CMD`, 예: `./gradlew compileTestJava --offline`) — 새로 쓴 테스트 클래스는 "실패에 실패"하기보다 컴파일에 실패하는 경우가 훨씬 많은데, 그걸 확인하려고 프레임워크 기동까지 포함된 전체 테스트 실행을 낼 필요가 없습니다. 컴파일 에러 1회당 full 실행 한 번씩을 절약합니다
- **`ALREADY_PASSES` 판정은 이미 존재하던 생산 코드를 겨냥한 테스트에만 적용됩니다** — RED가 방금 만든 stub을 호출하는 메서드는 정의상 통과할 수 없으므로 판정 대상이 아닙니다. RED의 테스트 실행이 확인하는 건 "stub이 예외를 던지는가"(이미 아는 사실)가 아니라 "테스트가 그 메서드에 도달하는가"입니다 — 픽스처가 setup에서 터지면 Red처럼 보이지만 Red가 아니고, GREEN이 디스패치 하나를 통째로 날리며 알아냅니다
- **사이클 중 `clean` 금지** — 컴파일 결과물을 버려 매번 전체 재빌드를 유발 (각 phase 에이전트 프롬프트에 명시)
- **리뷰어는 이미 보고된 테스트 결과를 신뢰** — cycle reviewer에는 GREEN/픽스 에이전트의 결과를, final reviewer에는 오케스트레이터가 방금 돌린 스코프 실행 결과를 함께 넘겨서, 리뷰어가 같은 테스트를 다시 돌리지 않게 합니다. 정적 판독으로 풀리지 않는 구체적 의심이 있을 때만 예외
- **프로젝트 컨텍스트 1회 캡처** — 매 에이전트가 코드를 재탐색하던 오버헤드를 제거해 RED/GREEN 단계 자체의 지연을 줄임

## 주의사항

- 오케스트레이터는 파일을 직접 수정하지 않고 반드시 서브에이전트를 통해 위임합니다
- **REFACTOR 에이전트는 커밋하지 않습니다** — 스테이징·커밋은 오케스트레이터와 사용자의 결정이며, 사이클 종료 시 변경은 커밋되지 않은 상태로 남습니다
- 프로젝트 피드백 게이트가 있으면 그것을 따르고, 없으면 1번 사이클만 게이트한 뒤 이후 진행 방식을 한 번 물어봅니다
- Cycle Reviewer는 전달받은 diff와 불변성만 판단합니다 — 코드베이스 탐색(파일 열기뿐 아니라 grep·glob 검색 포함)은 금지입니다
- Final Reviewer는 양방향으로 대조합니다 — 불변성마다 **어기는 케이스와 지키는 케이스가 모두** 있는지(한쪽만 있으면 `PARTIAL`, Important 지적), 그리고 모든 새 테스트가 불변성이나 태스크로 거슬러 올라가는지(`ORPHAN`)
- 요구사항 문서가 없으면 요구사항 공유를 먼저 요청합니다
- 리뷰어에는 계획 문서가 아니라 `session.md`·`context.md`의 **확정된 태스크 목록·불변성**을 전달합니다 — 특정 문서 포맷에 의존하지 않습니다
